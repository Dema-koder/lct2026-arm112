# План приближения симулятора к оригиналу

Отфильтрованная выжимка из [frontend-improvements.md](frontend-improvements.md) под одну задачу: **прокликать тренажёр и понять интерфейс АРМ-112**.

Критерий отбора: пункт попадает в план, если он меняет **логику работы** (какие статусы есть, в каком порядке, каким жестом ставятся) или **то, что видно на экране**. Всё, что не видно при прокликивании — производительность, обработка ошибок, логирование, оценка грамотности, адаптив — вынесено в раздел «Сознательно не делаем».

Захардкоженные поля, которые выглядят логически верно (`Пострадавшие: нет`, `[ВИС] Класс: —`, `АРМ 12`, округ-заглушка), **остаются как есть** — они не мешают понять интерфейс и в оригинале выглядят ровно так же.

## Этап 1. Состояния и переходы

Самое важное: сейчас у карточки шесть состояний вместо девяти, а из «Не принята» нет выхода. Пока это не починено, прокликать реальный жизненный цикл невозможно.

### 1.1. Переименовать статусы в женский род

[page.tsx:16-23](../frontend/app/page.tsx#L16-L23):

```js
ACCEPTED: "Принята",        // было "Принято"
NOT_ACCEPTED: "Не принята", // было "Не принято"
```

Остальные подписи (`Добавлена`, `Начало реагирования`, `Отказ от выполнения работ`, `Работы завершены`) уже совпадают с оригиналом — не трогаем.

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md), таблица «Статусы реагирования службы».

**Объём:** 2 строки.

### 1.2. Добавить «Получена службой»

Технический статус, который в оригинале проставляется **автоматически при открытии карточки диспетчером на АРМ-112**. Сейчас факт открытия карточки нигде не фиксируется, и лента истории начинается сразу с «Принята».

Что сделать:

- backend: статус `RECEIVED_BY_SERVICE` + запись в timeline при первом `GET /cards/{id}`;
- фронтенд: `RECEIVED_BY_SERVICE: "Получена службой"` в `statusLabels`.

Это заметно при прокликивании: открыл карточку — в ленте появилась строка, как в боевой системе.

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md) — «Проставляется системой автоматически при… открытии карточки диспетчером на АРМ-112»; кадр `dds-12.png`.

### 1.3. Добавить «Прибытие» и «Проведение работ»

Между «Начало реагирования» и «Работы завершены» в оригинале два обязательных шага. Сейчас тренажёр их проскакивает.

Backend — enum `ReactionAction` в [ApiModels.java:59-64](../src/main/java/ru/lct/arm112/api/ApiModels.java#L59-L64), переходы в [TrainingEngine.java:161-184](../src/main/java/ru/lct/arm112/service/TrainingEngine.java#L161-L184) и список в [TrainingEngine.java:374-381](../src/main/java/ru/lct/arm112/service/TrainingEngine.java#L374-L381):

```
ACCEPTED          -> START_RESPONSE, REFUSE_WORK
RESPONSE_STARTED  -> ARRIVED, REFUSE_WORK              // новое
ARRIVED           -> WORK_IN_PROGRESS, REFUSE_WORK     // новое
WORK_IN_PROGRESS  -> COMPLETE, REFUSE_WORK             // новое
```

Фронтенд — две подписи в `statusLabels`, две кнопки в меню службы по `allowedActions` (меню уже строится от них, новая вёрстка не нужна).

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md), таблица статусов; там же «Типовые нарушения», пункт 6 — отсутствие статусов хода работ разбирается как типовая ошибка диспетчера, то есть в тренажёре эти шаги должны быть доступны и их пропуск должен быть заметен.

### 1.4. Разрешить «Не принята» → «Принята»

Проверено на живом backend: после `DECLINE` приходит `allowedActions: []`, карточка мертва.

Оригинал требует обратного — это единственный переход, доступный из «Не принята»:

> «При выборе статуса "Не принята" единственным доступным вариантом для последующего выбора будет статус "Принята"»

Что сделать: backend — разрешить переход `NOT_ACCEPTED → ACCEPTED` и вернуть `["ACCEPT"]` в `allowedActions`. Фронтенд менять не нужно, кнопка отрисуется сама.

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md), таблица статусов + раздел «Что делать если…» (первая строка).

**Почему важно для прокликивания:** это самый частый сюжет реальной работы — поставил «Не принята», позвонил отдел контроля, исправил на «Принята». Без него половина сценариев из памятки непроигрываема.

### 1.5. Убрать тупик с завершением занятия

[page.tsx:570](../frontend/app/page.tsx#L570) — кнопка «Завершить занятие» появляется только при статусе карточки `COMPLETED`. Поставил «Не принята» или «Отказ от выполнения работ» — занятие не сдать, хотя backend такой submit принимает (проверено).

Что сделать: перенести кнопку в шапку журнала, показывать всегда пока `sessionState === "ACTIVE"`.

**Объём:** перенос одной строки JSX.

## Этап 2. Жест проставления статуса

Сейчас статус ставится кликом по плитке службы внизу → открывается меню со всеми доступными действиями сразу. В оригинале — иначе, и это заметная часть того, «как работает интерфейс».

### 2.1. Карандаш в блоке службы

В оригинале статус проставляется **иконкой карандаша в правом верхнем углу блока оповещения своей службы** (виден на кадре `dds-12.png` рядом с кнопками «ЧС» и «ЧП»).

Комментарий авторов скриншотов дословно: «Далее при нажатии карандашика можно проставлять новые статусы (НАЧАЛО РЕАГИРОВАНИЯ / ОТКАЗ ОТ ВЫПОЛНЕНИЯ РАБОТ / РАБОТЫ ЗАВЕРШЕНЫ) и комментарии».

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md), «Механика в интерфейсе»; [screenshots/README.md](../docs/materials/screenshots/README.md).

### 2.2. Последовательный выбор из двух уровней

Оригинал, дословно: «Выбрать статусы реагирования **можно только последовательно**. Т.е. сначала в выпадающем списке будет только 2 первичных статуса: "Принята" и "Не принята". При выборе статуса "Принята" откроется выпадающий список со статусами "Начало реагирования", "Прибытие", "Проведение работ", "Завершение работ" и "Отказ от выполнения работ"».

Перечисление пяти статусов во второй фразе — это состав второго уровня в целом, **а не набор доступных одновременно**. Перепрыгнуть через статус нельзя: цепочка строгая, шаг за шагом.

Исключение одно — «Отказ от выполнения работ»: он доступен на любом этапе после приёма как выход из цепочки.

Меню строится от `allowedActions` с backend, поэтому после этапа 1.3 два уровня и строгий порядок получаются сами.

**Известные нюансы для будущей проработки:** памятка отдельно оговаривает, что Служба 103 не проставляет «Не принята» и «Отказ от выполнения работ», а вместо них ставит «Работы завершены: Завершение работ без бригады» — то есть для отдельных служб цепочка короче. Пока не реализовано.

### 2.3. Форма ввода статуса как в оригинале

Кадр `dds-16.png`: поверх панели служб появляется строка — выпадающий список `Статус`, числовое поле, поле `Комментарий`, справа кнопки ✓ и ✕.

Сейчас вместо неё модальное окно по центру экрана. Модалка удобнее, но узнаваемость теряется; перенести форму вниз, к панели служб — недорого.

### 2.4. Плитки служб: своё время и свой статус

Три правки в одном месте, [page.tsx:563-568](../frontend/app/page.tsx#L563-L568):

- **время**: сейчас `new Date()` — на плитке тикают текущие часы. Нужно время проставления статуса из `timeline`. В оригинале: `11:14 Добавлена`, `11:29 Начало реаги…`;
- **подпись**: `service.label.includes("Пожар") ? "Служба 101" : ...` → `Служба {service.code}` (поле `code` уже приходит с backend и равно `"101"`);
- **статус**: все плитки показывают общий `card.status`. В оригинале у каждой службы свой статус, и редактировать можно **только свою**; чужие видно, но они неактивны.

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md), «Механика в интерфейсе» («в свёрнутом блоке отображается последний статус реагирования и время его проставления») и правило 2 «соответствие компетенции службы»; [card-ui.md](../docs/materials/card-ui.md), раздел «Службы».

### 2.5. Хронология в прямом порядке

[page.tsx:554](../frontend/app/page.tsx#L554): убрать `.reverse()`. В оригинале лента строго сверху вниз по времени:

Заодно вывести автора события — `actorLabel` приходит с backend и сейчас не отображается.

**Объём:** удалить один вызов, добавить одно поле.

## Этап 3. Внешний вид

Дёшево и сразу видно.

### 3.1. Панель служб: серая, активная плитка синяя

**Важно:** оранжевая нижняя панель — это экран **оператора-112** (кадры `card-01.png`, `card-06.png`, `card-09.png`), где внизу лежит кнопка «сохранить». На АРМ **ДДС**, который мы и симулируем, панель служб **серо-синяя** (`~#5A6A72`), оранжевого на этом экране нет вовсе.

Что действительно отличается от оригинала на кадре `dds-12.png`:

- активная (раскрытая) плитка службы — **синяя**, в тон ленте истории над ней; у нас была тёмно-серая;
- у каждой плитки сверху маленький шеврон `^` для раскрытия, у активной — иконка карандаша (см. п. 2.1);
- раскрытая плитка визуально приподнята над панелью, лента истории выходит из неё.

```css
.service-dock { background: #5a6a72; }
.service-tile.active { background: #0784c6; }
```

Объявленный в [globals.css:14](../frontend/app/globals.css#L14) `--orange: #f06435` остаётся неиспользованным — и правильно: он понадобится, только если будет делаться экран оператора-112.

**Эталон:** [screenshots/README.md](../docs/materials/screenshots/README.md), таблица «Палитра и типографика»; кадры `dds-12.png`, `dds-16.png`.

Обратный отсчёт для тренажёра с нормативом 3 минуты полезнее — предлагаю оставить его, но **перенести в правый верхний угол и оформить как в оригинале**, показывая оба числа: затрачено / осталось.

## Этап 4. Если останется время

Эти пункты заметно добавляют достоверности, но каждый дороже всего этапа 3.

### 4.1. Показать реальный состав служб

Сейчас в доке одна плитка. По ЕКП на происшествие оповещается в среднем **16.5 служб**, и нижняя панель оригинала выглядит так: `ОАТИ`, `Поселение Ти…`, `Поселение Во…`, `Служба 101`, `Служба 104`, `Служба 102`, `Деп. ЖКХ`, `ЦЭМП`, `ЦОДД`, `Мос.Без.`, `Мослифт`.

Именно эта лента делает экран узнаваемым. Данные готовы — [data/classifier.json](../docs/materials/data/classifier.json), достаточно положить в демо-карточку список служб из строки ЕКП для «пожар: мусор».

Требует правки backend (состав `assignedServices`), но не логики — плитки уже рендерятся циклом.

**Эталон:** [classifier.md](../docs/materials/classifier.md); кадр `dds-12.png`.

### 4.2. Горячие клавиши

В оригинале карточка полностью управляется с клавиатуры, потому что цель — «как можно быстрее забивать данные». Полная таблица перенесена в [card-ui.md](../docs/materials/card-ui.md), раздел «Горячие клавиши».

Для прокликивания хватит четырёх: `Esc` — закрыть карточку, `Alt+A` — к адресу, `Alt+T` — к блоку «Что случилось», `Alt+S` — сохранить/подтвердить. Плюс подсказки по зажатию `Alt`, как в оригинале.

### 4.3. Расширенный поиск

Надпись «расширенный по параметрам⌄» сейчас ничего не раскрывает. В оригинале раскрывается панель с поиском по типу происшествия, признакам, адресу, округу, району, описательному адресу, региону и службе.

Достаточно раскрывающейся панели с 3-4 полями — эксперт почти наверняка нажмёт на эту надпись.

**Эталон:** [dds-workflow.md](../docs/materials/dds-workflow.md), «Поиск карточки происшествия».

### 4.4. Звук исходящего вызова

Сейчас звонок молча проскакивает в `ACKNOWLEDGED` за 0.67 с, стадии `RINGING` нет вовсе, поля `CallMedia` приходят пустыми, поле `CallTarget.voice` (`MALE`/`FEMALE`) не используется.

Заказчик описывал сценарий буквально: набрать 3-4-значный номер → услышать «Слушаю вас» → произнести → услышать «Я вас понял, информация принята»; голоса мужские и женские с разными интонациями.

Минимум для прокликивания: задержка 2-3 секунды в состоянии `RINGING` и два коротких аудиофайла. Без этого «симулятор IP-телефонии» на демонстрации не звучит.

**Эталон:** [q-and-a.md](../docs/materials/q-and-a.md), раздел 9.
