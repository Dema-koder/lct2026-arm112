## 1. После восстановления копии — не показан экран входа

**Что происходит.** `BackupService.restore` поднимает `auth_version` у всех пользователей, старые JWT становятся недействительными (это правильно). Но фронтенд узнаёт об этом только по первому `401`, а обрабатывает `401` лишь `TraineeShell` при загрузке контекста ([TraineeShell.tsx:28](../frontend/app/components/trainee/TraineeShell.tsx#L28)). Преподаватель и администратор видят красный баннер «Учётная запись заблокирована…» и продолжают сидеть на экране с мёртвым токеном. Сам администратор, который нажал «восстановить», тоже остаётся на экране «Система».

**Что сделать.**

1. `frontend/lib/api.ts`: в `request()` добавить общий перехват — при `response.status === 401` вызвать зарегистрированный обработчик до выброса `ApiError`:
   ```ts
   let unauthorizedHandler: (() => void) | null = null;
   export const onUnauthorized = (handler: (() => void) | null) => { unauthorizedHandler = handler; };
   // в request(): if (response.status === 401 && !path.startsWith("/auth/login")) unauthorizedHandler?.();
   ```
2. `frontend/app/page.tsx`: в `useEffect` зарегистрировать `onUnauthorized(logout)`, при размонтировании снять. `logout` уже чистит `sessionStorage` и состояние — экран входа появится сам.
3. `AdminShell → System.restore`: после успешного `204` не делать `await load()` (он тут же получит 401), а сразу вызвать `onLogout()` с тостом «База восстановлена — войдите заново». Для этого пробросить `onLogout` в `System` из `AdminShell`.
4. WebSocket: в `useSocket` при закрытии сокета с кодом 1008/4401 (сервер отклонил тикет) — не переподключаться бесконечно, а вызвать тот же обработчик. Сейчас сокет молча переподключается каждые 1,8 с с невалидным токеном.
5. Убрать частный обработчик из `TraineeShell.tsx:28` — станет лишним.
6. Тест: в `rendered-html.test.mjs` проверить наличие `onUnauthorized` в `api.ts` и `page.tsx`; ручная проверка — `BKP-4` из [docs/TEST_PLAN.md](../docs/TEST_PLAN.md).

**Побочный эффект.** Любая блокировка/смена пароля другим администратором тоже будет мгновенно выбрасывать на вход во всех вкладках — это и требовалось в SEC-1…SEC-5.

## 2. Оценка преподавателя по критериям и с комментариями

**Что происходит.** `TeacherAssessment {total, comment}` ([ApiModels.java:189](../src/main/java/ru/lct/arm112/api/ApiModels.java#L189)) — один балл и один комментарий на сессию. Преподаватель хочет ставить балл и комментарий по каждому критерию (время, адрес, тип, службы, грамотность / время, действия, коммуникация, грамотность) — и чтобы итог считался из них.

**Что сделать.**

1. Миграция `V7__teacher_criteria.sql` (можно объединить с п. 3 в одну V7):
   ```sql
   alter table assessment add column teacher_payload text;   -- JSON: критерии преподавателя
   ```
2. Модель:
   ```java
   public record CriterionScore(@NotBlank String code, @Min(0) @Max(100) Double score, @Size(max = 1000) String comment) {}
   public record TeacherAssessment(@Min(0) @Max(100) Double total, @Size(max = 2000) String comment,
                                   List<CriterionScore> criteria) {}
   ```
   Правило: если `criteria` переданы, `total` вычисляется сервером по весам режима (те же веса, что у `CardFillAssessor` / `CardActionsAssessor`, вынести их в общий `AssessmentWeights`); переданный `total` игнорируется. Если `criteria` пусты — как сейчас, только `total`. Критерий без `score` (только комментарий) в расчёт не входит, берётся балл ИИ.
3. `Assessment` (ответ): добавить `teacherCriteria: List<CriterionScore>`; в `AssessmentRepository.finalOf` — при наличии оценки преподавателя по критерию подменять соответствующий `timingScore` / `addressScore` / … на неё, чтобы «Мои результаты» и отчёт показывали итоговые значения по критериям, а не только общий балл. Оценка ИИ по критериям сохраняется в `ai_payload` и отдаётся как есть в `aiTotalScore` + новый `aiCriteria`.
4. `LessonService.assess`: валидировать коды критериев по режиму (`CARD_FILL`: `timing, address, classification, services, language`; `CARD_ACTIONS`: `timing, actions, communication, language`), пересчитать итог, `setTeacher(id, teacherId, total, comment, payload)`.
5. Отчёт: `ReportRow` без изменений (итог уже `finalTotal`); в CSV добавить колонки по критериям с итоговыми значениями — преподаватель хотел видеть, «за что».
6. Контракт `0.3.1`: `TeacherAssessment.criteria`, `Assessment.teacherCriteria`, `Assessment.aiCriteria`.
7. Фронтенд `SessionReview`: вместо двух полей — таблица «Критерий | Оценка ИИ | Оценка преподавателя | Комментарий», строка на критерий, внизу «Итог (считается автоматически)» и общий комментарий. Поле балла пустое = оставить оценку ИИ. `AssessmentView` обучающегося: у критерия с оценкой преподавателя — пометка и комментарий под строкой.
8. Тест: `TeacherFlowIntegrationTest` — `PUT` с `criteria` по двум критериям, проверить, что `totalScore` пересчитан по весам и `teacherCriteria` вернулись; обучающемуся после публикации видны комментарии по критериям.

## 7. Описание тренировок: последовательность вводных

**Что происходит.** Обучающийся получает вводные строго по очереди: следующая появляется только после сохранения текущей (режим заполнения) или закрытия карточки (режим ДДС). В реальной системе оператор 112 видит журнал всех карточек, может открыть любую и создаёт новую, когда принял вызов. Это надо проговорить в документации и в интерфейсе, чтобы на защите не выглядело как незнание предметной области.

**Что сделать.**

1. `docs/ROLES.md`, раздел 1 (диаграмма) — абзац «Отличие учебной подачи от боевой»: вводные подаются последовательно как учебное упрощение (Q&A §4: «преподаватель либо даёт команду на генерацию, либо пересылает заранее заготовленные»); в боевом ПОВ-112 у оператора — журнал и создание карточки по принятому вызову; переход к этому — п. 4 ниже.
2. `docs/TESTING_ROLES.md`, раздел 3.1, первая строка таблицы — та же оговорка одним предложением.
3. `README.md`, «Реализовано → Обучающийся» — пометка «(вводные подаются последовательно — учебное упрощение, см. ROLES.md)».
4. Интерфейс преподавателя, `LessonCreate`, подсказка под полем «Режим» для `CARD_FILL`: «Вводные выдаются по одной; следующая — после сохранения текущей».
5. Интерфейс обучающегося, шапка экрана заполнения рядом с «в очереди ещё N»: тултип с тем же текстом.

## 4. Режим оператора 112: как это устроено в боевой системе и что менять

### Как работает реальный оператор 112 (по [card-ui.md](../docs/materials/card-ui.md), [q-and-a.md](../docs/materials/q-and-a.md) §4, [screenshots](../docs/materials/screenshots/README.md))

1. Оператор сидит в **журнале происшествий** — тот же список, что у ДДС (`dds-05.png`): номер, дата, время, тип, адрес, статус. Видит свои и чужие карточки смены, может открыть любую на просмотр или **дополнение** («внесение дополнений», «добавление отработки» — [card-ui.md](../docs/materials/card-ui.md), «Работа с карточкой после сохранения»).
2. Приходит **входящий вызов** — телефонная полоса сверху показывает АОН, оператор принимает звонок. В этот момент он **создаёт новую карточку** (пустая форма `card-01.png`): АОН уже подставлен, таймер `00:00` пошёл.
3. Слушая заявителя, заполняет адрес (уточняет ориентир до формализованного), «что случилось» через плашки/поиск, опросную карту, описание. Службы подтягиваются автоматически.
4. Нажимает **«сохранить»** — карточка уходит на сервер и в ДДС; оператор возвращается в журнал, где она появилась со статусом «Добавлена». Следующий вызов может прийти в любой момент, в том числе пока карточка ещё не сохранена (Q&A §7, «многозадачность»).
5. Повторный звонок по тому же происшествию — оператор находит карточку в журнале (поиск) и **дополняет** её, а не создаёт дубль («Не принята: дубль» — типовое нарушение ДДС).

### Чем отличается тренажёр сейчас

- Нет журнала в режиме заполнения: обучающийся видит только текущую форму.
- Вводная приходит текстом сразу в форму, без стадии «входящий вызов → принять → создать карточку».
- Сохранённую карточку нельзя открыть и дополнить.
- Следующая вводная строго после сохранения; параллельных вызовов нет.

### Пошаговый план доведения до боевой логики

Этап A — журнал и создание карточки (2 дня).

1. `CardFillService`: отделить «вводная получена» от «карточка создана». Новая сущность в `SessionState`: `IncomingCall {id, scenarioId, receivedAt, state: RINGING | TAKEN | MISSED}`. При старте занятия и по таймеру (`settings: fill.call_interval_seconds`, по умолчанию 0 = следующий после сохранения, как сейчас) движок кладёт вызов в очередь и публикует `call.incoming`.
2. Эндпоинты: `GET /incoming-calls?sessionId=` (текущие вызовы), `POST /incoming-calls/{id}/take` → создаёт `CardDraft` с АОН и таймером и возвращает его (замена `POST /card-drafts`); `POST /card-drafts` оставить для «создать карточку без вызова» — на защите так удобнее показывать пустую форму.
3. Экран обучающегося: **журнал** как у ДДС (переиспользовать `IncidentJournal` с колонками оригинала), строки — сохранённые и текущие карточки сессии; сверху телефонная полоса (`phone-strip` уже есть): входящий вызов мигает «Входящий · +7 916 …», кнопка «Принять» → форма. Кнопка «Новая карточка» в шапке журнала (в оригинале — тоже есть).
4. Норматив: 30 секунд от `call.incoming` до `take` — тот же `sla.acceptance_seconds`; в оценку — `CALL_ANSWER_OVERDUE`. Пропущенный вызов через 60 с → `MISSED`, в оценку критично.
5. Монитор преподавателя: колонка «Вызовов: принято/пропущено».

Этап B — дополнение сохранённой карточки (1 день).

6. `POST /card-drafts/{id}/amend` → переводит `SAVED` в `AMENDING`, разрешает PATCH `description` (дописывание, старый текст не редактируется — как «внесение дополнений» в оригинале) и `flags`; `save` пишет запись в ленту `Дополнение`. Адрес и тип после сохранения не меняются — в оригинале это тоже так.
7. Журнал: клик по сохранённой строке — просмотр с кнопкой «дополнение».
8. Оценка: дополнение по повторному вызову вместо новой карточки — плюс; дубль — минус (`DUPLICATE_CARD`, если адрес и тип совпадают с уже сохранённой).

Этап C — многозадачность (0,5 дня).

9. `fill.call_interval_seconds > 0` — вызовы приходят по расписанию независимо от сохранения; несколько черновиков одновременно; форма переключается через журнал. В оценке — время реакции на каждый вызов.

Полное проектное описание потока событий — расписание смены, параллельные вызовы и карточки, повторные обращения, дубли, звонок отдела контроля, оценка потока, управление интенсивностью у преподавателя — вынесено в [realistic-flow-design.md](realistic-flow-design.md).

## 8. Мелкий интерфейс на маленьких дисплеях

**Что происходит.** Базовый размер шрифта 13px, служебные подписи 9–12px и все размеры в абсолютных пикселях — как в оригинале ПОВ-112, рассчитанном на 24-дюймовые мониторы. На ноутбуке 13–14" с 1366×768 текст журнала нечитаем. Переверстать всё в `rem`/`clamp()` — сотни правил в двух CSS-файлах.

**Что сделано.**

1. Масштаб интерфейса через CSS `zoom` на `body` с переменной `--ui-scale` (поддерживается всеми актуальными браузерами, включая Firefox ≥ 126). Раскладка внутри считает, что окно уже в `1/scale` раз, поэтому существующие media-запросы журнала (≤ 1500 / ≤ 1250px) продолжают работать по реальной ширине окна.
2. Авто-значение по ширине экрана (`window.screen.width`): ≤ 1366 → 120%, ≤ 1600 → 110%, иначе 100%.
3. Кнопки `A− NN% A+` в шапке (`TopStrip`), диапазон 80–160%, шаг 10%, значение в `localStorage` (`arm112-ui-scale`) — свой для каждого браузера, как настройка рабочего места.
4. Самые мелкие подписи 9px подняты до 10px.

**Что ещё можно сделать, если мало.** Перевести `.incident-row`, `.timeline` и `.service-tile` на `rem` с `html { font-size: clamp(13px, 0.85vw + 5px, 16px) }` — тогда журнал будет расти плавно вместе с окном; это ~40 правил в `globals.css`, около половины дня.
