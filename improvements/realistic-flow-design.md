# Занятие, близкое к боевой смене: параллельные карточки, вызовы, повторные обращения

Проектное описание того, как превратить нынешнюю «очередь вводных по одной» в поток событий, похожий на реальную смену оператора 112 и диспетчера ДДС. Развивает п. 4 из [manual-testing-fixes.md](manual-testing-fixes.md); решения по ролям и режимам — в [docs/ROLES.md](../docs/ROLES.md).

Первоисточники: [q-and-a.md](../docs/materials/q-and-a.md) §4 (как устроено в реальности), §7 (нормативы и многозадачность), §19 (сложность через веса); [dds-workflow.md](../docs/materials/dds-workflow.md) (четыре правила, семь типовых нарушений, «что делать если»); [card-ui.md](../docs/materials/card-ui.md) («Работа с карточкой после сохранения», «Телефония»).

---

## 1. Чем боевая смена отличается от нынешнего занятия

| | Сейчас в тренажёре | В боевой системе |
|---|---|---|
| Как приходит работа | Вводная появляется в форме сразу; следующая — только после сохранения/закрытия текущей | Входящий вызов (оператор 112) или новая строка в журнале (ДДС) — в любой момент, в том числе пока открыта другая карточка |
| Сколько карточек одновременно | Одна | Несколько: одна открыта, две ждут в журнале, по третьей звонит заявитель повторно |
| Где живут карточки | Только текущая форма (оператор 112) / журнал только своей сессии (ДДС) | Журнал смены со всеми карточками: своими, чужими, закрытыми; поиск; открытие на просмотр и дополнение |
| Повторные обращения | Нет | Заявитель звонит второй раз по тому же происшествию; в ДДС приходит вторая карточка по тому же адресу — надо распознать дубль |
| Изменение обстановки | Нет | Отдел контроля звонит по ошибочному отказу; «ситуация изменилась, нужны другие службы»; заявитель уточняет адрес |
| Что оценивается | Одна карточка в вакууме | Приоритизация: кого принять первым, что можно отложить, реакция на повторный вызов, отсутствие дублей |

Q&A §7 дословно: «пока обучаемый работает с одной карточкой, может появиться новая. Здесь будет интересно решение: чтобы человек не «залипал» на одну карточку три минуты, а стремился к следующей. Именно на скорости и возникают ошибки».

## 2. Принципы

1. **Занятие — это сценарий смены, а не список вводных.** Преподаватель задаёт не «5 билетов», а расписание событий: когда приходит вызов, когда повторный, когда звонит отдел контроля. Простая форма расписания генерируется из списка билетов и уровня интенсивности автоматически.
2. **События идут по часам сессии, независимо от действий обучающегося.** Норматив 30 секунд считается от появления события в журнале/телефонной полосе, а не от того, когда обучающийся закрыл предыдущую карточку (решение №12 в ROLES.md).
3. **Журнал — главный экран.** Форма карточки открывается из журнала и возвращает в журнал; в обоих режимах.
4. **Учебные упрощения объявляются явно**, а не маскируются: нет голоса заявителя (Q&A §9 — исключён), нет чужих операторов в журнале (можно подмешать «фоновые» карточки, см. 4.4).
5. **Интенсивность — параметр сложности** (Q&A §19: сложность через веса), ставится преподавателем или предлагается по сложности сценариев; адаптация под обучающегося — по-прежнему не автоматизируется (ROLES.md, раздел 6).
6. **Оценка учитывает поток**: время реакции на каждое событие, пропущенные вызовы, дубли, приоритизация — сверх нынешних критериев, не вместо.

## 3. Модель: сценарий смены

### 3.1. Сущности

```
lesson                    ← как сейчас + intensity {CALM|NORMAL|STORM|CUSTOM}, timelineMode {SEQUENTIAL|SCHEDULED}

shift_event (в снимке сессии, генерируется при старте)
  id, sessionId, kind, scheduledAt (секунды от старта сессии), scenarioId?, relatedCardId?,
  state {PENDING|ACTIVE|HANDLED|MISSED|EXPIRED}, activatedAt, handledAt, payload

kind:
  INCOMING_CALL      — вызов заявителя (режим оператора 112): звонит, надо принять и создать карточку
  REPEAT_CALL        — повторный вызов по уже сохранённой карточке: надо найти и дополнить, не создавать дубль
  CARD_DELIVERED     — карточка пришла в журнал ДДС (режим ДДС), как сейчас card.created
  DUPLICATE_CARD     — вторая карточка по тому же адресу/поводу в ДДС: ожидается «Не принята: дубль, реагирование по КП …»
  CONTROL_CALL       — звонок отдела контроля по ошибочному отказу: ожидается исправление на «Принята»
  SITUATION_UPDATE   — дополнительная информация от 112 («ситуация изменилась»): ожидается комментарий/дополнение
  BACKGROUND_CARD    — чужая карточка смены в журнале: трогать не надо, только для реалистичности и поиска
```

`SEQUENTIAL` — текущее поведение (следующее событие после закрытия предыдущего) — остаётся как режим «делай, как я» и для первого занятия. `SCHEDULED` — по расписанию.

### 3.2. Генерация расписания из билетов

Преподаватель выбирает N сценариев и интенсивность; движок строит расписание при старте сессии (каждому обучающемуся своё, но из одних сценариев — сравнимость в отчёте):

| Интенсивность | Интервал между первичными событиями | Наложение (новое приходит, пока открыта карточка) | Повторные/контрольные |
|---|---|---|---|
| CALM | 240 с (больше норматива 3 мин) | нет | нет |
| NORMAL | 120 с | 50% событий | 1 повторный вызов на 3 сценария |
| STORM | 45–60 с | всегда | повторные на каждый второй, 1 контрольный звонок, 1 дубль |
| CUSTOM | преподаватель задаёт вручную в таблице (событие, смещение, сценарий) | | |

Правила генерации:
- первое событие — через 5 с после старта;
- `REPEAT_CALL` ставится через 90–180 с после `INCOMING_CALL` того же сценария, и только если сценарий помечен `repeatable` (в билетах это «звонки несколько часов», «много повторных обращений» — типовые нарушения 2 и 6);
- `DUPLICATE_CARD` (ДДС) — второй сценарий с тем же адресом и типом через 60–120 с после первого;
- `CONTROL_CALL` — планируется условно: срабатывает через 60 с после того, как обучающийся поставил «Не принята» на карточке с `expectedDecision = ACCEPT` (обратная связь по нарушению 3);
- `SITUATION_UPDATE` — через 150 с после принятия карточки с признаком `escalates` в сценарии («нужны другие службы»);
- `BACKGROUND_CARD` — 3–8 карточек чужих операторов/служб при старте, статусы «Завершена»/«Начало реагирования», разные адреса; их нельзя открыть на редактирование.

Событие с `scheduledAt` в будущем ждёт; движок раз в секунду (тот же `detectOverdue`) переводит `PENDING → ACTIVE`, публикует событие в WebSocket и запускает норматив.

### 3.3. Что такое «обработать» событие

| Событие | Обработано, когда | Пропущено, когда |
|---|---|---|
| INCOMING_CALL | обучающийся нажал «Принять» (создан черновик с АОН) | 60 с без ответа → MISSED, вызов исчезает из полосы; в оценке критично |
| REPEAT_CALL | принял и открыл существующую карточку на дополнение (`amend`) — или создал новую (тогда HANDLED, но в оценке `DUPLICATE_CREATED`) | 60 с без ответа |
| CARD_DELIVERED | как сейчас: карточка доведена до терминального статуса | 30 с без открытия → просрочка принятия (уже есть) |
| DUPLICATE_CARD | «Не принята» с комментарием, содержащим номер основной карточки или слово «дубль» | принята и отработана как самостоятельная → `DUPLICATE_ACCEPTED` |
| CONTROL_CALL | исходящий/входящий диалог принят, затем на карточке «Принята» | статус не исправлен за 120 с |
| SITUATION_UPDATE | добавлен комментарий к карточке (ДДС) или дополнение (оператор 112) в течение 120 с | иначе `UPDATE_IGNORED` |

## 4. Режим оператора 112: журнал, вызовы, дополнения

### 4.1. Экран

Три состояния одного экрана, переключаются без перезагрузки:

1. **Журнал** (по умолчанию) — тот же `IncidentJournal`, что у ДДС, колонки оригинала; строки: свои сохранённые карточки, свои открытые черновики (статус «Набор», таймер), фоновые карточки смены. Шапка: кнопка **«Новая карточка»** (в оригинале есть — создание без вызова, например по звонку с прямого телефона).
2. **Телефонная полоса** — над журналом и над формой, всегда видна. Входящий вызов: мигает «Входящий · +7 916 …», кнопка «Принять» и таймер ожидания. Несколько вызовов подряд — очередь в полосе (второй «ждёт»). Принятый вызов открывает форму с АОН и запускает таймер карточки.
3. **Форма карточки** — текущая `FillWorkspace` без изменений; «сохранить» возвращает в журнал. Кнопка «‹ журнал» без сохранения — черновик остаётся открытым (в журнале «Набор»), таймер идёт.

### 4.2. Повторный вызов и дополнение

- `REPEAT_CALL` приходит с тем же АОН и тем же `scenarioId`; текст вводной — «повторная»: «Я уже звонил, приехали? Добавьте, что …». 
- Правильное действие: принять → найти карточку в журнале (поиск по номеру/адресу/АОН уже есть) → **«дополнение»** (`POST /card-drafts/{id}/amend`): открывается форма только-чтение с блоком «Дополнение» (текст, флаги) — как «внесение дополнений» в инструкции. Сохранение пишет запись в ленту карточки `AMENDED` с автором и временем.
- Неправильное: «Новая карточка» и сохранение второй карточки с тем же адресом/типом → в оценке `DUPLICATE_CREATED` (в ДДС такие карточки и порождают «Не принята: дубль»).
- Подсказка в тренировке при принятом повторном вызове: «Заявитель уже обращался — найдите карточку в журнале».

### 4.3. Параллельные черновики

- Открытых черновиков может быть несколько; у каждого свой таймер 3 минуты от принятия вызова.
- Вызов, принятый во время заполнения другой карточки, **не** закрывает текущую форму: полоса предлагает «Принять и открыть» (текущий черновик остаётся в журнале) или «Отклонить» (вызов ждёт до 60 с).
- Оценка времени — по каждой карточке от `takenAt` до `savedAt`; плюс общий показатель «среднее время ответа на вызов».

### 4.4. Фоновые карточки

Чтобы журнал выглядел как смена: при старте добавляются 3–8 карточек из библиотеки с пометкой `background=true`, чужими операторами («оп. 3», «оп. 7»), статусами и временем в прошлом. Их можно открыть на просмотр, поиск по ним работает; оценка их не учитывает. Это же даёт материал для `DUPLICATE_CARD` в ДДС и для поиска при повторном вызове.

## 5. Режим ДДС: поток карточек и связь с 112

### 5.1. Несколько карточек в журнале

Уже реализовано на уровне движка (`pending`), меняется только правило доставки: по расписанию, а не после закрытия. Журнал ДДС уже умеет несколько строк, таймеры и красную индикацию. Добавить:
- звуковой/визуальный сигнал новой строки (мигание заголовка «Список происшествий», счётчик непринятых);
- сортировку: непринятые сверху, по времени поступления.

### 5.2. Дубль

Вторая карточка по тому же адресу и типу. Правильно — «Не принята» с комментарием «дубль, реагирование по КП <номер>». Подсказка в тренировке: «По этому адресу уже есть карточка № …». В оценке: принял обе и отработал как две — `DUPLICATE_ACCEPTED` (нарушение 4 памятки: «следовало "Не принята: дубль"»).

### 5.3. Звонок отдела контроля

Если на карточке с ожидаемым «Принять» обучающийся поставил «Не принята», через 60 с в телефонной полосе — **входящий** от «Отдел контроля 694-71-89» с текстом: «По карточке № … вы отказались, происшествие в вашей компетенции, примите». Принять звонок → ожидается «Принята» (переход из «Не принята» уже разрешён). Исправил — `DECLINE_CORRECTED` (уже есть, INFO); не исправил за 120 с — `CONTROL_IGNORED` (WARNING). Это ровно сюжет «ошибочно проставили "Не принята"» из «что делать если».

### 5.4. Ситуация изменилась

Для сценариев с `escalates=true` через 150 с после «Принята» приходит `SITUATION_UPDATE`: строка в ленте карточки от «Оператор 112»: «Дополнение: на месте обнаружен пострадавший, нужна 103». Ожидается комментарий диспетчера (любой статус хода работ с комментарием, упоминающим передачу информации) — правило 4 памятки «делитесь информацией». Нет реакции — `UPDATE_IGNORED`.

### 5.5. Исходящий звонок как сейчас, плюс входящие

Телефонная полоса ДДС получает входящие (отдел контроля, руководитель с вопросом «что по карточке №…»). Ответ — кнопка «Принять» и выбор реплики из 2–3 вариантов (голоса нет, Q&A §9): это дешёвый способ проверить, знает ли обучающийся состояние своих карточек.

## 6. Оценка потока

Новые критерии добавляются к существующим весам как отдельная группа «Работа в потоке» (вес 20 внутри `CARD_ACTIONS` и `CARD_FILL`; остальные веса пропорционально ужимаются — правится в одном месте, `AssessmentWeights`).

| Код | Условие | Тяжесть |
|---|---|---|
| `CALL_MISSED` | вызов не принят за 60 с | CRITICAL |
| `CALL_ANSWER_SLOW` | ответ позже 30 с | WARNING |
| `DUPLICATE_CREATED` | вторая карточка по тому же поводу вместо дополнения | WARNING |
| `DUPLICATE_ACCEPTED` | дубль в ДДС принят как самостоятельная карточка | WARNING |
| `CONTROL_IGNORED` | звонок отдела контроля без исправления статуса | WARNING |
| `UPDATE_IGNORED` | дополнение от 112 без реакции | WARNING |
| `PRIORITY_INVERSION` | принята более поздняя карточка, пока более ранняя просрочена | INFO |
| `STALLED_ON_CARD` | одна карточка держалась > 3 мин при ждущих в журнале (Q&A §7 «залипать») | INFO |

В отчёте преподавателя: колонки «Вызовов принято/пропущено», «Среднее время ответа», «Дублей». В мониторе — счётчик активных событий у каждого обучающегося и красная пометка при пропущенном вызове.

## 7. Управление преподавателем

- В форме занятия: **интенсивность** (выпадающий список CALM/NORMAL/STORM + «настроить»), для CUSTOM — таблица событий: тип, через сколько секунд, сценарий, привязка к другому событию.
- **Кнопка «Событие»** в мониторе во время занятия: вручную отправить обучающемуся (или всем) вызов/карточку/звонок отдела контроля сейчас — «делай, как я» и импровизация на защите.
- **Пауза занятия**: останавливает часы сессии (нормативы не текут) — для разбора у доски.
- Предустановки по методике Q&A §10 «от простого к сложному»: первое занятие SEQUENTIAL, второе CALM, зачёт NORMAL/STORM.

## 8. Изменения в коде

### Бэкенд
- `SessionState`: `List<ShiftEvent> events`, часы сессии (`startedAt`, `pausedAt`, накопленная пауза); снимок `TrainingSnapshot` расширяется — миграций таблиц нет, кроме `lesson.intensity`, `lesson.timeline_mode` (`V8`).
- `ShiftScheduler` (новый сервис): генерация расписания из сценариев и интенсивности; `@Scheduled(1s)` активация событий, пометка MISSED, условные события (CONTROL_CALL, SITUATION_UPDATE).
- `CardFillService`: `takeCall(eventId)` → черновик с АОН; `amend(draftId)` / `saveAmendment`; несколько открытых черновиков; `start` без вызова остаётся («Новая карточка»).
- `TrainingEngine`: доставка карточек по событиям вместо `afterCardChange`; `DUPLICATE_CARD` и `SITUATION_UPDATE` как записи в ленте; входящие звонки в полосе (`IncomingCall` с репликами).
- Эндпоинты: `GET /shift-events?sessionId=`, `POST /shift-events/{id}/take`, `POST /shift-events/{id}/decline`, `POST /card-drafts/{id}/amend`, `POST /card-drafts/{id}/amendments`; преподавателю `POST /teacher/lessons/{id}/events` (ручное событие), `POST /teacher/lessons/{id}/pause|resume`.
- События WebSocket: `shift.event_activated`, `shift.event_missed`, `call.incoming`, `card.amended`.
- Оценка: `FlowAssessor` поверх существующих; сценарий получает `repeatable`, `escalates`, `duplicateOf`.

### Фронтенд
- Оператор 112: `FillShell` = телефонная полоса + журнал (переиспользовать `IncidentJournal`) + форма; очередь вызовов; «дополнение».
- ДДС: входящие в полосе, счётчик непринятых, подсказки дубля.
- Преподаватель: интенсивность и таблица событий, кнопка «Событие», пауза; отчёт с новыми колонками.

### Этапы
1. Расписание и `SCHEDULED` для ДДС (карточки по часам, дубль, отдел контроля) — 2 дня; всё на существующем журнале.
2. Журнал и входящие вызовы у оператора 112, параллельные черновики — 2 дня.
3. Повторный вызов и дополнение — 1 день.
4. Оценка потока, отчёт, ручные события и пауза у преподавателя — 1,5 дня.
5. Фоновые карточки и входящие «реплики» — 1 день.

Итого ~7–8 дней; после этапа 1 уже есть что показывать (Q&A §7 «многозадачность» закрыт для ДДС).

## 9. Открытые вопросы

1. **Нужен ли голос для входящих** (отдел контроля, руководитель)? Q&A §9 исключает голос заявителя, но диалог ДДС → руководитель ожидался голосовым. Предложение: текст + короткий аудиофайл-заглушка «Слушаю вас», как в плане fidelity 4.4.
2. **Пропущенный вызов** — исчезает или остаётся в журнале как «пропущенный вызов» с возможностью перезвонить? В боевой системе перезвон возможен. Предложение: остаётся 5 минут с кнопкой «Перезвонить» (создаёт карточку со штрафом времени).
3. **Одинаковое ли расписание у всех участников** занятия? Для сравнимости в отчёте — да; для «списывания» между соседями — вредно. Предложение: одинаковые сценарии, смещения ±15%.
4. **Пауза и нормативы**: пауза преподавателя честна для всех; собственная пауза обучающегося — нет (в бою её не бывает). Не давать.
5. **Фоновые карточки в оценке** — точно не учитывать; но открытие чужой карточки на редактирование в оригинале возможно (дополнение по чужой карточке при повторном звонке). Разрешить дополнение и чужих? Предложение: да, с пометкой автора — это и есть реальный сценарий «повторный звонок попал другому оператору».
