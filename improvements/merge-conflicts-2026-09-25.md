## 2. Суть расхождения

Обе ветки отвечают на вопрос «когда обучающийся получает следующую вводную», и отвечают по-разному.

### В `main`: расписание с фиксированным шагом

```
schedulePendingCards(state)   // разложить вводные по времени заранее
deliverDueCards(state, now)   // отдать те, чьё время пришло
```

- шаг задаётся настройкой `simulation.card_arrival_ms` (по умолчанию 8 секунд) из `V8__realistic_simulation_settings.sql`;
- вводные выдаются лениво — при опросе `GET /cards` и при старте;
- есть масштаб времени служб `simulation.service_time_scale_percent` = 25 %, чтобы за показ успевало приехать несколько служб;
- **только для режима ДДС.** Для режима оператора 112 при старте не делается ничего.

### В ветке оценки: интенсивность и очередь вызовов

```
Intensity.SEQUENTIAL | LOW | MEDIUM | HIGH   // интервал и число фоновых карточек
arriveNextCall / presentNextCall             // очередь входящих вызовов
backgroundCards                              // чужие карточки в журнале 112
```

- интервал случайный в диапазоне, зависит от выбранной преподавателем интенсивности;
- для оператора 112 есть полноценная телефония: вызов звонит 30 секунд, пропущенный перезванивает через 20, после двух пропусков теряется;
- интенсивность хранится в `lesson.intensity` (миграция `V13`) и выбирается в интерфейсе (`Lessons.tsx`);
- на пропущенных и потерянных вызовах построена часть оценки (`CALL_MISSED`, `CALL_LOST`).

### Чего нет в чужой ветке

| Механизм | `main` | ветка оценки |
|---|---|---|
| `deliverDueCards`, `schedulePendingCards` | есть | нет |
| `Intensity`, `arriveNextCall`, `backgroundCards` | нет | есть |
| Колонки `lesson.service_code`, `lesson.intensity` | нет | есть (V13) |
| Настройки `simulation.*` | есть (V8) | нет |

Родословная: `fix/manual-testing-round-2` (интенсивность) в `main` **не вливалась** — там только `round-1`. Дальше линии разошлись.

## 3. Чем это грозит, если слить механически

- **Взять версию `main`** — пропадёт телефония оператора 112, интенсивность занятия и фоновые карточки. Сломается оценка: правила `CALL_MISSED` и `CALL_LOST` останутся без источника событий, а `LessonService` продолжит требовать корректную интенсивность при создании занятия.
- **Взять версию ветки оценки** — пропадут управляемые задержки показа, ради которых заводилась `V8`. Настройки `simulation.*` останутся в базе неиспользуемыми.
- **Склеить наспех** — получится два планировщика, спорящих за `state.pending`. Это худший вариант: сломается не сразу и не очевидно.

---

## 4. Что предлагаю

Механизмы **не исключают друг друга**: они про разные режимы и разные уровни.

1. **Режим ДДС** — взять расписание из `main`. Оно новее, уже развёрнуто и решает задачу показа: за время демонстрации успевают приехать несколько служб.
2. **Режим оператора 112** — оставить очередь вызовов из ветки оценки. В `main` для этого режима нет ничего, терять нечего.
3. **Интенсивность** — сохранить как множитель к шагу расписания, а не как отдельный планировщик: `шаг = card_arrival_ms × коэффициент(интенсивность)`. Тогда и настройка из `V8` работает, и выбор преподавателя в интерфейсе что-то значит.
4. Настройку `simulation.service_time_scale_percent` оставить как есть — она про длительность работы служб и с доставкой вводных не пересекается.

Это примерно полдня работы и требует прогона `GoldenRunHarness` в строгом режиме: прогоны `R07` (пропущенный вызов), `R11` (три вводные подряд) и `R15` (прокликивание) проверяют ровно затронутое.
