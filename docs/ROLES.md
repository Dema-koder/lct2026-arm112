# Роли учебного сервиса и место симулятора АРМ-112 в нём

Симулятор АРМ-112 в репозитории — это **рабочее место обучающегося**, один из трёх экранов сервиса. ТЗ и Q&A описывают сервис целиком: три роли, учебный процесс, отчётность. Этот документ фиксирует принятые решения, план реализации, права ролей и то, что ещё не решено.

Источники: [task-spec.md](materials/task-spec.md), [q-and-a.md](materials/q-and-a.md) (разделы 3, 4, 8, 10, 11, 15, 16, 19), [card-ui.md](materials/card-ui.md), [dds-workflow.md](materials/dds-workflow.md). Где Q&A расходится с ТЗ, прав Q&A. Решения из раздела 5 согласованы с командой 2026-09-19 и имеют приоритет над предположениями в других документах.

## 1. Как роли ложатся на процесс

В реальной системе-112 цепочка: заявитель → оператор 112 → сервер 112 → ДДС. Заявитель из задачи исключён (Q&A §4, §9). Обучающийся отрабатывает **оба** оставшихся звена — по решению №6 сервис учит и заполнению карточки (роль оператора 112), и ведению статусов (роль диспетчера ДДС). Преподаватель заменяет всё, что вокруг: подаёт вводные, раздаёт, оценивает.

```
                ┌──────────────────────────────────────┐
                │  Преподаватель (+ ИИ)                │  формирует вводные (билеты / генерация),
                │                                      │  назначает занятия, видит всех, оценивает,
                │                                      │  публикует результаты; его слово выше ИИ
                └──────────────┬───────────────────────┘
                               │ персональное занятие каждому
          ┌────────────────────┼─────────────────────┐
          ▼                    ▼                      ▼
   ┌─────────────┐      ┌─────────────┐        ┌─────────────┐
   │ Обучающийся │      │ Обучающийся │  ...   │ Обучающийся │
   │ АРМ 4       │      │ АРМ 7       │        │ АРМ 12      │   номер АРМ — из учётной записи
   ├─────────────┤      ├─────────────┤        ├─────────────┤
   │ режим       │      │             │        │             │
   │ ЗАПОЛНЕНИЕ  │──┐   │             │        │             │   = экран оператора 112 (card-*.png):
   │ КАРТОЧКИ    │  │   │             │        │             │     адрес, «что случилось», опросная
   ├─────────────┤  │   │             │        │             │     карта, службы, описание, сохранить
   │ режим       │  │   │             │        │             │
   │ ДЕЙСТВИЯ С  │◄─┘   │             │        │             │   = экран ДДС (dds-*.png, текущий фронтенд):
   │ КАРТОЧКОЙ   │      │             │        │             │     принять за 30 с, статусы, звонок
   └─────────────┘      └─────────────┘        └─────────────┘

   Карточки, сохранённые в режиме ЗАПОЛНЕНИЯ, могут попадать в журналы режима ДЕЙСТВИЙ
   (источник «сформированные обучающимися», ТЗ сценарий 3).
```

**Поток вводных.** Преподаватель задаёт в занятии интенсивность: «по одной» (следующая вводная — после сохранения или закрытия текущей, как в Q&A §4), «низкая» (1,5–3 мин), «средняя» (45–90 с), «высокая» (15–40 с). При заданной интенсивности вводные приходят по таймеру независимо от того, закрыта ли текущая. У диспетчера ДДС они появляются в журнале — он сам выбирает, какую открыть; у оператора 112 звонит входящий вызов (30 секунд на ответ, иначе заявитель перезванивает через 20 с, после второго пропуска — не дозвонился), карточка создаётся по принятому вызову, а на главном экране — журнал смены с сохранёнными и фоновыми карточками других АРМ. В режиме ДДС преподаватель выбирает службу обучающегося (по умолчанию 101); её плитка всегда на карточке, даже если тип непрофильный — тогда правильное действие «Не принята» с основанием. Не реализованные пока элементы боевой смены (повторные звонки по карточке, дубли, контрольные звонки) — [improvements/realistic-flow-design.md](../improvements/realistic-flow-design.md).

```

   ┌──────────────────────────────────────────────────────┐
   │ Администратор: учётки, АРМ, настройки, журналы, бэкап│  вне учебного процесса, всё через UI
   └──────────────────────────────────────────────────────┘
```

## 2. Роли по ТЗ и Q&A

| Роль | Кто это в жизни | Что делает (ТЗ) | Уточнения Q&A |
|---|---|---|---|
| **Администратор** | ИТ-специалист учебного центра | Запуск/остановка сервисов, мониторинг, обновление ПО, резервное копирование; учётные записи, роли, блокировка; настройка телефонии, БД, политик доступа, журналирования; просмотр системных журналов | Отдельный логин и уровень доступа; 2FA не нужна (§15) |
| **Преподаватель** | Методист/инструктор ДДС | Выбор категорий событий, настройка генерации; формирование и **подтверждение эталона**; предпросмотр вопросов с подсветкой правильных; коррекция комментарием; загрузка материалов; **адресная раздача заданий по рабочим местам**; старт/завершение занятия; отчёт | Рабочее место на отдельном ПК в контуре, видит действия всех обучаемых (§16); в конфликте с ИИ всегда прав (§3, §8); веса сложности 1–10 ставит вручную или принимает от ИИ (§19) |
| **Обучающийся** | Будущий оператор 112 / диспетчер ДДС | Назначенные сценарии и материалы; практические задания; приём сообщений; ввод текста в карточку; **свои** результаты, статистика, ошибки, рекомендации; таймер | Занятия только офлайн в классе (§10); уровень может меняться по результатам (§11) — пока не реализуем, см. раздел 6 |

Запреты для обучающегося — прямым текстом в ТЗ: административные и преподавательские функции, изменение учебных материалов, удаление результатов, изменение настроек, доступ к результатам других обучающихся.

## 4. Целевая модель данных

Следствие решений №1, №2, №4, №5, №6, №10. Названия — предварительные, для миграций `V2+`.

```
app_user            id, login, password_hash, display_name, role {ADMIN|TEACHER|TRAINEE},
                    workstation_number (для TRAINEE, задаёт администратор), group_id?, active

training_group      id, name, teacher_id                         ← рейтинг группы считается по ней

lesson              id, teacher_id, group_id, kind {TRAINING|CHECK|EXAM},
                    mode {CARD_FILL|CARD_ACTIONS}, card_source {GENERATED|TRAINEE_MADE|MIXED},
                    state, started_at, completed_at, results_published_at?
                    — «занятие» глазами преподавателя: одна раздача группе

training_session    id, lesson_id, trainee_id, workstation_number (копия из app_user на момент старта),
                    state, started_at, completed_at
                    — персональное занятие одного обучающегося (решение №1);
                      это то, что сейчас называется «активная сессия»

scenario            id, source {TICKET|GENERATED|TRAINEE_MADE}, category, difficulty 1..10,
                    caller_text, expected_address, expected_incident_types[], expected_services[],
                    reference_confirmed_by?, reference_confirmed_at?
                    — билеты из tickets.md как сид; эталон — см. раздел 6, п. «Эталон»

card                session_id, scenario_id, mode, status, … поля по card-ui.md …
                    author_trainee_id? (для карточек, сформированных в CARD_FILL)

card_timeline       card_id, actor_user_id?, actor_role, action, comment, at

outbound_call       как сейчас + session_id

assessment          session_id, ai_* (баллы, ошибки, рекомендации),
                    teacher_* (баллы, комментарий, teacher_id, at) — nullable,
                    final = teacher_* если есть, иначе ai_*                         (решение №5)

audit_event         id, actor_user_id, role, action, resource_type, resource_id,
                    occurred_at, request_id, ip, payload                               (решение №4)
                    — отдельный журнал по всем ролям, хранение ≥ 6 месяцев
```

Рейтинг: `rating(trainee) = взвешенное среднее final-оценок по сложности сценария`; `rating(group)` — агрегат по участникам. Формулу утверждаем вместе с методикой оценки; таблица не нужна, считается запросом или materialized view.

## 5. Принятые решения по неясностям

Нумерация сохранена от первой версии документа. Решения 3 и 7 остаются открытыми — вынесены в раздел 6.

| # | Вопрос | Решение | Что это меняет |
|---|---|---|---|
| 1 | Единица изоляции данных | **Каждый обучающийся получает персональное занятие** (`training_session` на человека). Занятие преподавателя (`lesson`) — контейнер над ними. Учитываем будущую подстройку уровня под обучающегося и **рейтинговый балл группы** | Снимок `training_state` перестаёт быть глобальным; карточки, звонки, оценка, события — всё на `session_id`; появляется `training_group` |
| 2 | Что такое рабочее место | **Привязка к учётной записи.** Номер компьютера хранится у пользователя и подтягивается в занятие и отчёт автоматически | `app_user.workstation_number`, копия в `training_session` на старте; реестр АРМ — колонка, не отдельная сущность |
| 4 | Аудит | **Отдельный журнал по всем действиям всех ролей, хранение 6 месяцев** | `audit_event`, запись из всех командных эндпоинтов всех трёх ролей; политика хранения — настройка администратора, минимум 6 мес |
| 5 | Оценка преподавателя vs ИИ | **Хранится рядом с оценкой ИИ.** Итоговая = оценка преподавателя, если она есть, иначе оценка ИИ | `assessment.teacher_*` nullable, `final` вычисляется; в отчёте и рейтинге используется только `final` |
| 6 | Режим заполнения карточки | **Реализуем, и начинаем именно с него** | Новый режим `CARD_FILL`, экран оператора 112, источник карточек «сформированные обучающимися» становится реальным. См. этап 1 |
| 8 | Видимость чужих занятий | **Преподаватель видит только свои занятия и отчёты** | Фильтр `teacher_id` во всех `/teacher/**` |
| 9 | Администрирование | **Кнопки в UI**, не только документ | Этап 5: сервисы, бэкап, настройки — через экран |
| 10 | Когда обучающийся видит результат | **Зависит от вида занятия:** тренировка — подсказки прямо по ходу; проверка — результат сразу по окончании; зачёт — только после того, как преподаватель просмотрел, оценил и опубликовал | `lesson.kind {TRAINING|CHECK|EXAM}`, `results_published_at`, действие «Опубликовать» у преподавателя |

## 6. Что ещё не решено

### Эталон (бывшая неясность №3) — открыто

Не решено, потому что не решено, чему учим в первую очередь: **ведению статусов** (ДДС) или **заполнению первой карточки** (оператор 112). После решения №6 оба режима существуют, поэтому эталон должен быть **разным по режиму**, и это уже можно проектировать, не дожидаясь приоритета:

| Режим | Из чего состоит эталон | Откуда берётся | Что сравниваем |
|---|---|---|---|
| `CARD_FILL` | формализованный адрес; тип(ы) происшествия; признаки опросной карты; состав служб | **Уже есть в материалах:** адрес курсивом в [tickets.md](materials/tickets.md) — это и есть «правильный ответ»; тип и службы — из [classifier.json](materials/data/classifier.json) по строке ЕКП | адрес обучающегося ↔ эталонный (главный критерий по Q&A §6, кейс «Дубнинская/Дубининская»); тип ↔ тип; службы ↔ службы; грамотность описания; время |
| `CARD_ACTIONS` | решение принять/не принять с обоснованием; ожидаемая цепочка статусов; обязательность звонка; ключевые слова комментария | Из памятки ДДС и билета; для отказа — категория обоснования из [dds-workflow.md](materials/dds-workflow.md) («не в компетенции», «дубль», …) | цепочка ↔ цепочка; отказ обоснован или нет; звонок сделан; комментарий содержательный; нормативы 30 с / 3 мин |

Цена, если структуру выбрать неверно, — 3–5 дней на движок оценки и экран подтверждения. Рекомендация: хранить эталон как JSON с дискриминатором `mode`, начать с `CARD_FILL` (данные готовы), а вопрос «что важнее» решать по первым прогонам с преподавателем.

### Адаптивная сложность (бывшая неясность №7) — **не трогаем**

Под «адаптивной сложностью» могут пониматься разные параметры (вес сценария, число одновременных карточек, наличие подсказок, время на карточку, число служб). Что именно и как подстраивать — определится после того, как появятся реальные результаты занятий.

**Явно не реализуем сейчас:** автоматическую смену уровня, поле «уровень» у обучающегося, предложения ИИ по сложности. Что закладываем, чтобы потом не переделывать: `scenario.difficulty` (1–10, ставит преподаватель, Q&A §19) и персональные `training_session` (решение №1) — этого достаточно, чтобы адаптацию добавить поверх без миграции данных.

## 7. План реализации

Порядок отражает решение №6: интерфейс заполнения карточки — первым. Фундамент ролей (этап 2) можно вести параллельно на бэкенде, он не мешает этапу 1. Каждый этап — отдельная запись в [history/](../history/).

### Этап 1. Режим заполнения карточки (`CARD_FILL`)

Экран оператора 112 по [card-ui.md](materials/card-ui.md) и кадрам `card-*.png`. Оранжевая панель здесь — правильно (`--orange: #f06435` в `globals.css` наконец пригодится).

Бэкенд:
- `scenario` с сидом из 96 билетов; `caller_text` — текст «со слов заявителя», `expected_address` — курсивное уточнение из билета.
- `POST /cards` (создание черновика по сценарию), `PUT /cards/{id}` (сохранение полей), `POST /cards/{id}/save` — финальное сохранение, останавливает таймер, запускает оценку.
- Автоподбор служб по классификатору при выборе типа + адреса (поведение оригинала: «список формируется автоматически»; ручное добавление есть, удаление — нет).
- Оценка `CARD_FILL`: адрес, тип, службы, грамотность, время. Первая версия — детерминированная сверка с эталоном, ИИ поверх — позже.

Фронтенд, блоки экрана в порядке оригинала:
- заявитель и три телефона (заполнены из сценария, редактируемы);
- формализованный адрес: страна/субъект/округ/район/улица/дом/корпус/строение/квартира/подъезд/этаж + **описательный адрес** — главное учебное поле;
- флаги «Пострадавшие / Отказ от скорой / Заблокированные / нет контакта / срыв звонка»;
- «Что случилось?»: часто используемые плашки + поиск по строке + значимые типы; несколько типов;
- опросная карта по выбранному типу (плоский список вопросов, ответы кнопками, последний — свободный текст); признаки синим; строка `Класс.: …`;
- описание со слов заявителя, счётчик `0 / 1999`;
- нижняя оранжевая панель служб, автоподбор, «+»;
- таймер `00:09 минут / секунд` справа вверху, номер карточки, «Опер., АРМ N»;
- кнопка «сохранить» — единственная кнопка действия на экране.

Вводная обучающемуся подаётся текстом билета (заявитель исключён, Q&A §9). Куда его положить, не ломая вид оригинала, — в правую панель под таймером или как всплывающую «трубку»; решить на макете.

### Этап 2. Учётные записи, RBAC, аудит

- `app_user` в `V2`, сид `admin` / `teacher` / `trainee`; `AuthController.login` — по БД; роль в JWT — из БД.
- `SecurityConfig`: `/api/v1/admin/**` → `ADMIN`, `/api/v1/teacher/**` → `TEACHER`, остальное учебное → `TRAINEE`; `@EnableMethodSecurity` для проверок «моя сессия / моя карточка».
- Контракт: `User.role` → `enum [ADMIN, TEACHER, TRAINEE]` — **ломающее**, версия `0.3`.
- `audit_event` и аспект/фильтр, пишущий каждую команду каждой роли; ретеншен — параметр, по умолчанию 6 месяцев, ниже опустить нельзя.
- Фронтенд: маршрутизация по роли после входа; экран входа общий.

### Этап 3. Занятия, персональные сессии, группы, рейтинг

- `training_group`, `lesson`, `training_session`; `TrainingEngine` перестаёт быть синглтоном состояния — становится сервисом над `session_id`.
- Снимок `training_state` разъезжается на таблицы (`card`, `card_timeline`, `outbound_call`, `assessment`) с ключом `session_id`; `realtime_event` уже имеет `session_id` — оставляем.
- `GET /cards`, WebSocket-события, replay — только своя сессия обучающегося.
- `lesson.kind` определяет видимость результата (решение №10): `TRAINING` — подсказки в реальном времени; `CHECK` — `assessment` отдаётся по `completed_at`; `EXAM` — только после `results_published_at`.
- Рейтинг обучающегося и группы — расчёт по `final`-оценкам, взвешенный `scenario.difficulty`.

### Этап 4. Рабочее место преподавателя

В стиле АРМ-112, без лишних кнопок. Экраны:

1. **Сценарии** — библиотека билетов и сгенерированных; категория, сложность 1–10, эталон (по режиму) с подтверждением и правкой комментарием.
2. **Занятие** — создать: группа, вид (тренировка / проверка / зачёт), режим (`CARD_FILL` / `CARD_ACTIONS`), источник карточек (сгенерированные / сформированные обучающимися / смешанно), сценарии; чекбоксы по обучающимся (АРМ подтягивается из учётки); «Начать».
3. **Монитор** — таблица обучающихся текущего занятия: АРМ, статус карточки, таймеры, просрочки; тот же поток `card.*`-событий.
4. **Завершить занятие** → отчёт (§16): фамилия, АРМ, оценка по времени, число синтаксических ошибок, уровень подготовки; таблица + графики; CSV. Только свои занятия (решение №8).
5. **Оценка** — карточка результата: оценка ИИ, поле оценки преподавателя и комментарий; после сохранения `final` = преподавателя. Для зачёта — кнопка «Опубликовать» (решение №10); появляется только у `EXAM`.
6. **Материалы** — загрузка DOCX/PDF/XLSX, назначение группе.

### Этап 5. Рабочее место администратора

Всё в UI (решение №9):

1. Пользователи: создать, роль, **номер АРМ**, группа, блокировка, сброс пароля.
2. Группы: создать, назначить преподавателя.
3. Настройки: симуляция телефонии (задержка `RINGING`, голоса), уровни логирования, срок хранения аудита (≥ 6 мес).
4. Журналы: `audit_event` с фильтрами по пользователю / роли / действию / периоду; системный лог ошибок.
5. Сервисы: health backend / БД / WebSocket; «Сделать резервную копию сейчас», расписание, список копий, «Восстановить из копии» с подтверждением.

### Этап 6. Обучающийся: результаты и материалы

- «Мои результаты» — по занятиям, с учётом вида: тренировка — подсказки были по ходу, здесь итог; проверка — сразу; зачёт — после публикации, до неё «на проверке у преподавателя».
- Материалы, назначенные группе.
- Рейтинг: свой и место в группе.

Допущения, которых нет в ТЗ (утверждены вместе с решениями):

- **Администратор не видит учебное содержание, результаты и оценки.** Его функции по ТЗ эксплуатационные; «кто настраивает систему» и «кто оценивает людей» разделены. Один человек в двух ролях — две учётки.
- **Преподаватель не удаляет результаты**, только помечает недействительными; данные нужны отчётности и дообучению.
- **Преподаватель может выполнять действия за обучающегося** («делай, как я», Q&A §10) — с `actor_role = TEACHER` в timeline, чтобы не попало в оценку.
- **Правило видимости результата** (решение №10) действует и для «Мои результаты», и для ответов API: до публикации зачёта `GET /assessments/{id}` обучающемуся возвращает `403`, а не пустую оценку.

## 10. Минимум для защиты

Если этапы 1–6 целиком не успеваем, вот что подтверждает решения заказчика с наименьшими затратами:

1. **Этап 1** — экран заполнения карточки с сидом из билетов и детерминированной оценкой адреса/типа/служб. Это единственное, чего в прототипе нет вообще, и это то, с чего решено начинать.
2. **Этап 2** целиком — без него «три роли» на защите не подтверждаются ничем.
3. Из этапа 3 — `lesson` + `training_session` на обучающегося, фильтрация по своей сессии, `kind` с тремя правилами видимости.
4. Из этапа 4 — П4 (создать занятие и начать), П5 (монитор), П7 (завершить и отчёт таблицей), П8 (оценка преподавателя рядом с ИИ).
5. Из этапа 5 — А1 (создать пользователя с номером АРМ) и А3 (журнал аудита списком).

Демонстрация: администратор завёл двух обучающихся с АРМ 4 и АРМ 7 → преподаватель создал «проверку» в режиме заполнения по двум билетам, выбрал обоих, нажал «Начать» → на двух браузерах открылась карточка оператора 112 с вводной → оба сохранили → преподаватель видит оба результата, одному ставит свою оценку → отчёт с рейтингом. Затем те же карточки — в занятие режима действий как «сформированные обучающимися». Это сценарии 2 и 3 из ТЗ подряд.
