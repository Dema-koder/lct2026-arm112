# Метрики тренажёра: учебные, метрики успешности, технические

Третий документ в связке: [ASSESSMENT_AND_SCENARIOS.md](ASSESSMENT_AND_SCENARIOS.md) — как оценка устроена сейчас, [ASSESSMENT_ML_ROADMAP.md](ASSESSMENT_ML_ROADMAP.md) — чем заменить правила на модели, здесь — **что измерять и как проверить, что это работает**.

Логика документа: сначала метрики для двух живых пользователей (преподаватель и обучающийся), из них выводятся метрики успешности продукта, затем технические метрики для каждого инструмента с моделью или статистикой, и в конце — что из этого проверяемо и чем.

Все метрики привязаны к реальным полям: `assessment` (`ai_payload` с `issues`, `ai_total`, `teacher_total`, `teacher_payload`, `timing_score`, `language_score`, `syntax_errors`), `training_session`, `lesson`, `scenario`, `realtime_event` (полный поток событий сессии с `sequence_number` и `occurred_at`), `audit_event`.

## 1. Что уже можно посчитать, а что требует доработки

| Источник | Есть сейчас | Чего не хватает |
|---|---|---|
| `assessment.ai_payload` | баллы по критериям, `issues` с кодами и severity, рекомендации | issues не разложены в таблицу — только JSON, агрегировать неудобно |
| `assessment.teacher_payload` | баллы преподавателя по критериям | нет отметки «согласен с ИИ» (сейчас согласие = отсутствие правки) |
| `realtime_event` | вся хронология сессии: `draft.created/updated/saved`, `call.incoming/missed/lost/answered`, `card.*`, `assessment.*` | `draft.updated` не хранит, **какое поле** изменилось — без этого нет траектории заполнения (п. 2.5 роадмапа) |
| `training_session` | старт/финиш сессии | — |
| `scenario` | `difficulty` (вручную), `referenceConfirmed` | нет эмпирической сложности (п. 2.6 роадмапа) |
| `audit_event` | все действия с ролью, статусом HTTP и временем | — |

**Вывод:** метрики §2–§4, помеченные значком ⚙, требуют сначала разложить `issues` в отдельную таблицу и добавить в `draft.updated` имя изменённого поля. Это две небольшие правки, после которых открывается почти вся аналитика без единой модели.

## 2. Метрики для обучающегося

Цель — не «оценка 73», а понимание, что именно делать иначе. Показываются на экране результатов после занятия (для зачёта — после публикации).

### 2.1 Результат занятия

| Метрика | Как считается | Что даёт обучающемуся |
|---|---|---|
| Итог и разложение по критериям | `finalOf`: балл преподавателя там, где задан, иначе ИИ | Видно, какой критерий утопил результат, а не только общий балл |
| Вклад критерия в потерю | `(100 − балл) × вес / 100` | «Адрес стоил вам 24 балла из 40» — сильнее, чем процент |
| Топ-3 ошибки по коду issue ⚙ | группировка `issues` по `code`, сортировка по severity и частоте | Конкретное «что повторяется», а не список из 20 замечаний |
| Критические ошибки | число issues с `severity = CRITICAL` | Отдельный счётчик: ошибки, из-за которых службы уедут не туда |
| Карточки, доведённые до конца | доля `SAVED` / терминальных статусов от числа вводных | Отличает «сделал плохо» от «не успел» |

### 2.2 Время и темп

| Метрика | Как считается | Зачем |
|---|---|---|
| Соблюдение нормативов | доля карточек в пределах 30 с / 3 мин | Прямое требование ТЗ, понятная цифра |
| Медиана времени на карточку | по `savedAt − startedAt` | Устойчивее среднего при одной «зависшей» карточке |
| Время до адреса и до типа ⚙ | по траектории заполнения (п. 2.5 роадмапа) | Показывает *где* теряется время внутри карточки |
| Доля пауз бездействия ⚙ | суммарные промежутки > 20 с без `draft.updated` | Отличает «думал» от «печатал медленно» |
| Перцентиль по группе | ранг медианы среди одногруппников | Относительная норма вместо абсолютного порога |
| Принятых вызовов с первого раза | `1 − missedCalls / всего вызовов` | Метрика реакции на звонок, сейчас видна только как штраф |
| Потерянные вызовы | `lost.size()` | Самое тяжёлое событие смены — должно быть отдельной строкой |

### 2.3 Прогресс

| Метрика | Как считается | Зачем |
|---|---|---|
| Кривая обучения | итог по номеру сессии (`training_session.started_at`) | Виден рост, а не только текущая точка |
| Тренд по критерию | линейная регрессия балла критерия по сессиям | «Адрес улучшается, время стоит на месте» |
| Повторяемость ошибки ⚙ | доля сессий подряд, где встречается код issue | Отличает случайную ошибку от закрепившейся привычки |
| Рейтинг и место в группе | `RatingService` | Есть сейчас; после п. 2.6 роадмапа — взвесить по сложности |
| Покрытие типов происшествий | сколько категорий классификатора отработано | Показывает пробелы: «ни одного газового вызова» |

### 2.4 Качество работы (не время)

| Метрика | Как считается |
|---|---|
| Точность адреса | средний балл `address`, отдельно доля точных попаданий в улицу |
| Точность типа | доля карточек с полным совпадением `expectedIncidentTypes` |
| Полнота служб | доля ожидаемых служб, попавших в карточку (recall по службам) |
| Ошибки компетенции (ДДС) | число `REFUSED_PROFILE_INCIDENT` + `ACCEPTED_FOREIGN_INCIDENT` |
| Грамотность | `syntax_errors` на 100 слов, а не абсолютное число |

## 3. Метрики для преподавателя

Цель — за минуту понять, что делать со следующим занятием: кого дотягивать, какую тему разобрать, какой сценарий переделать.

### 3.1 Мониторинг живого занятия

Уже частично есть в `LessonMonitor`; ниже — что стоит добавить.

| Метрика | Как считается | Зачем |
|---|---|---|
| Прогресс по каждому | done / total (есть) | — |
| Светофор риска | есть просрочка ИЛИ пауза > 60 с ИЛИ 2+ пропущенных вызова | Кому подойти прямо сейчас |
| Темп группы | медианное время на карточку в реальном времени | Понять, что интенсивность взята не та |
| Незанятые АРМ | сессии `PENDING` при `ACTIVE` занятии | Кто не зашёл |

### 3.2 Разбор после занятия

| Метрика | Как считается | Зачем |
|---|---|---|
| Распределение итогов | гистограмма + медиана и разброс | Провал группы или провал двух человек — разные выводы |
| Топ ошибок группы ⚙ | частота кодов issue по всем сессиям занятия | «12 из 30 ошиблись в улице» — готовая тема для разбора |
| Ошибки по сценариям ⚙ | частота issue в разрезе `scenarioId` | Отделяет плохой сценарий от плохо усвоенной темы |
| Матрица «обучающийся × критерий» | тепловая карта баллов | Кому что дотягивать, видно одним взглядом |
| Расхождение ИИ и преподавателя | `teacher_total − ai_total`, по критериям | Где ИИ систематически ошибается (вход для калибровки, п. 2.7 роадмапа) |
| Время на проверку | `teacher_assessed_at − assessment.created_at` | Сколько занятие стоит преподавателю — метрика полезности ИИ |

### 3.3 Качество библиотеки сценариев

| Метрика | Как считается | Зачем |
|---|---|---|
| Эмпирическая сложность | средний балл по сценарию (далее — Раш, п. 2.6) | Сравнить с проставленным `difficulty` |
| Дискриминативность | корреляция балла за сценарий с итогом сессии | Сценарий, который все решают одинаково, ничего не измеряет |
| Подтверждённость эталона | доля `referenceConfirmed` по источникам | Сколько сгенерированного ещё не проверено |
| Доля правок после генерации | сколько `GENERATED` изменено через `PUT` до подтверждения | Прямая метрика качества генератора |
| Покрытие классификатора | сколько типов и категорий вообще представлено | Сейчас перекос: OTHER 32, FIRE 25, MEDICAL 25, GAS 2, UTILITY 1 |
| Неиспользуемые сценарии | ни разу не попали в занятие | Библиотека растёт, но работает её часть |

### 3.4 Работа самого преподавателя

| Метрика | Зачем |
|---|---|
| Доля занятий, доведённых до `COMPLETED` | Брошенные занятия — признак проблем с UX или со временем |
| Доля зачётов, где результаты опубликованы | Обучающиеся ждут результата; неопубликованный зачёт — тупик |
| Доля сессий с правкой оценки | Если 0 % — преподаватель не смотрит; если 100 % — ИИ бесполезен |

## 4. Метрики успешности (продукт и обучение)

Выводятся из §2–§3. Это то, что показывают заказчику: работает ли тренажёр как «помощник в повседневной работе» (главный критерий из Q&A).

### 4.1 Успешность обучения

| Метрика | Определение | Целевой ориентир |
|---|---|---|
| **Прирост за курс** | медианный итог последней сессии − первой, по обучающемуся | > +15 баллов |
| **Доля достигших норматива** | доля обучающихся, у которых ≥ 80 % карточек в пределах 30 с / 3 мин | > 70 % к концу курса |
| **Снижение критических ошибок** ⚙ | число CRITICAL на карточку: первые 3 сессии vs последние 3 | падение вдвое |
| **Удержание навыка** | балл в зачёте vs средний балл в тренировках | разрыв < 10 баллов (иначе тренируются «на тренажёр») |
| **Закрытие пробелов** ⚙ | доля кодов issue, исчезнувших у обучающегося после разбора темы | > 50 % |
| **Разброс в группе** | стандартное отклонение итогов по группе | сокращается к концу курса: отстающих подтянули |

### 4.2 Успешность продукта

| Метрика | Определение | Зачем |
|---|---|---|
| **Доверие к оценке ИИ** | доля сессий, где преподаватель не менял балл | Главная метрика: если преподаватель правит всё, ИИ не помогает |
| **Среднее расхождение с преподавателем** | MAE между `ai_total` и `teacher_total` | Цель — MAE ≤ 8 баллов по 100-балльной шкале |
| **Экономия времени преподавателя** | время на проверку занятия с ИИ vs ручной разбор (замер до/после) | Аргумент для заказчика в часах |
| **Доля сгенерированных сценариев, принятых без правок** | `confirm-reference` без предшествующего `PUT` | Качество генерации п. 2.8 роадмапа; цель > 60 % |
| **Занятий на преподавателя в неделю** | из `lesson.created_at` | Реальное использование, а не демо |
| **Доля доведённых до конца сессий** | `COMPLETED` / всех начатых | Падение = проблемы с UX или производительностью |
| **Полнота охвата служб** | сколько ДДС реально используется в занятиях | Заказчик прямо просил масштабируемость по службам |

### 4.3 Эксплуатация

| Метрика | Целевое значение | Источник |
|---|---|---|
| Отклик API (p95) | ≤ 2 с при 100 пользователях (требование ТЗ) | метрики Spring Boot Actuator |
| Отклик на пути «черновик» (p95) | ≤ 300 мс — норматив 3 минуты не должен тратиться на ожидание | `audit_event.occurred_at` + Actuator |
| Одновременных активных сессий без деградации | ≥ 30 (реальный класс), цель 100 | нагрузочный тест |
| Доля сессий, восстановленных после перезапуска | 100 % (`TrainingEngine.initialize`) | лог восстановления |
| Потерянных событий realtime | 0 (`sequence_number` без разрывов) | SQL-проверка непрерывности |
| Время восстановления из бэкапа | < 15 мин | учения по `BackupService` |

## 5. Технические метрики инструментов с моделями и статистикой

По одному разделу на каждый инструмент из [роадмапа](ASSESSMENT_ML_ROADMAP.md). Для каждого — метрика качества, порог приёмки и как проверить.

### 5.1 Сверка адреса (справочник + `pg_trgm`, п. 2.1)

| Метрика | Порог | Проверка |
|---|---|---|
| Точность классификации исхода (верно / опечатка / другая улица) | ≥ 95 % на размеченном наборе | Набор из 200 пар «эталон — ввод», размеченный вручную, включая пары реальных улиц («Дубнинская / Дубининская», «Тверская / Тверской проезд») |
| Доля ложных «опечаток» на реальных улицах | 0 % — ключевой кейс | Отдельный набор только из пар существующих улиц |
| Полнота справочника | ≥ 99 % улиц из сценариев находятся | SQL по `scenario.expected_address` |
| Задержка поиска (p95) | ≤ 50 мс | Бенчмарк на прогретом индексе |
| Задержка автодополнения (p95) | ≤ 150 мс | Тест эндпоинта под нагрузкой 30 RPS |

### 5.2 Классификатор типа происшествия (`rubert-tiny2`, п. 2.2)

| Метрика | Порог | Проверка |
|---|---|---|
| Accuracy top-1 / top-3 по типу | ≥ 70 % / ≥ 90 % | Кросс-валидация на 96 билетах, стратификация по категории |
| Accuracy по категории | ≥ 85 % | Та же выборка, метки свёрнуты до категории |
| Macro-F1 | ≥ 0.6 | Важнее accuracy: классы несбалансированы (GAS — 2 сценария) |
| Калибровка уверенности (ECE) | ≤ 0.1 | Если уверенность идёт в сложность сценария, она должна быть честной |
| Доля отказов от ответа | настраиваемая; при уверенности < порога — «не знаю» | Лучше промолчать, чем дать неверную подсказку в TRAINING |
| Задержка инференса (p95) | ≤ 50 мс на CPU | JMH-бенчмарк ONNX Runtime в JVM |
| Память | ≤ 600 МБ | Замер heap/off-heap после прогрева |

Отдельно: **влияние на оценку**. Изменение баллов после ввода иерархической близости типов не должно ломать ранжирование — проверяется корреляцией Спирмена старых и новых итогов на архивных сессиях (ожидаем ≥ 0.9; если ниже — разбираться, где именно разошлось).

### 5.3 Проверка грамотности (LanguageTool, п. 2.3)

| Метрика | Порог | Проверка |
|---|---|---|
| Precision по ошибкам | ≥ 0.9 | Ложные срабатывания дороже пропусков: обучающийся теряет доверие к системе |
| Recall по подсаженным ошибкам | ≥ 0.7 | Набор из 100 текстов с внесёнными ошибками известных типов |
| Ложные срабатывания на терминах и топонимах | 0 на контрольном списке | Список улиц, служб, аббревиатур ДДС — прогон и проверка «чисто» |
| Задержка (p95) | ≤ 500 мс на текст | Бенчмарк; инстанция `JLanguageTool` одна на приложение |
| Память | ≤ 2 ГБ | Замер после прогрева русской модели |
| Совместимость со старой шкалой | смещение среднего балла `language` ≤ 10 пунктов | Прогон на архивных описаниях; иначе шкала едет и старые результаты несравнимы |

### 5.4 Слоты в комментариях (п. 2.4)

| Метрика | Порог | Проверка |
|---|---|---|
| Согласие с преподавателем (Cohen's κ) | ≥ 0.6 | Метки «полный / неполный» от преподавателя из `teacher_payload` |
| Precision «неполный комментарий» | ≥ 0.85 | Несправедливый штраф хуже пропуска |
| Устойчивость к обходу | отписки «ок», «передано», «сделано» ловятся в 100 % | Фиксированный набор известных отписок в тестах |
| Задержка | ≤ 10 мс | Тривиально: словари и регулярки |

### 5.5 Временной анализ (п. 2.5)

Статистика, не модель, — но проверяемость нужна не меньше.

| Метрика | Порог | Проверка |
|---|---|---|
| Полнота траектории | ≥ 99 % `draft.updated` содержат имя поля | SQL по `realtime_event.payload` |
| Точность детектора прокликивания | precision ≥ 0.9 | Размеченные вручную сессии + синтетические «прокликанные» прогоны |
| Устойчивость перцентилей | не считать при n < 8 в группе | Юнит-тест на малых выборках: должна возвращаться «нет данных», а не ложный ранг |
| Корректность пауз | паузы не включают время, когда сессия была на паузе/переподключалась | Тест с искусственным разрывом WebSocket |
| Стоимость расчёта | ≤ 200 мс на сессию | Бенчмарк SQL на 100 сессиях |

### 5.6 Сложность по Рашу (п. 2.6)

| Метрика | Порог | Проверка |
|---|---|---|
| Сходимость оценки | достигнута при n ≥ 10 наблюдений на сценарий | Проверка на синтетических данных с известными параметрами |
| Корреляция с ручным `difficulty` | Спирмен ≥ 0.5 | Если ниже — либо ручные веса плохие, либо модель; повод для разбора с преподавателем |
| Стабильность между занятиями | изменение оценки сложности < 1 балла по 10-балльной шкале | Пересчёт после каждого занятия, сравнение |
| Доверительный интервал | показывается преподавателю; при широком — «данных мало» | Юнит-тест на 3 наблюдениях: система не должна утверждать сложность уверенно |
| Восстановление параметров | на синтетике ошибка ≤ 0.5 логита | Генерируем матрицу по известным параметрам, проверяем восстановление |

### 5.7 Калибровка по преподавателю (п. 2.7)

| Метрика | Порог | Проверка |
|---|---|---|
| MAE до и после калибровки | снижение ≥ 20 % | Кросс-валидация по занятиям: калибруем на прошлых, проверяем на новом |
| Отсутствие переобучения | MAE на отложенном занятии не растёт | Hold-out по занятию, не по сессии (иначе утечка внутри группы) |
| Минимум данных | не применять при < 30 пар оценок | Юнит-тест: при нехватке данных веса не меняются |
| Монотонность | калиброванный балл не убывает при росте исходного | Свойство изотонической регрессии, проверяется property-тестом |
| Обратимость | старые оценки пересчёту не подлежат | Тест: калибровка не меняет уже выставленные `final_total` |

### 5.8 Генерация сценариев (LLM, п. 2.8)

| Метрика | Порог | Проверка |
|---|---|---|
| Доля валидных по схеме | ≥ 98 % | Валидатор: адрес из справочника, тип из классификатора, службы по ЕКП |
| Доля принятых преподавателем без правок | ≥ 60 % | `confirm-reference` без предшествующего `PUT` — считается автоматически |
| Доля дублей | ≤ 5 % | Косинусная близость эмбеддингов к существующим сценариям > 0.95 |
| Разнообразие | доля уникальных типов в пачке ≥ 70 % | Чтобы генератор не выдавал десять вариаций одного пожара |
| Отсутствие утечки эталона в текст | 0 случаев | Проверка, что `callerText` не содержит формализованный адрес и название типа дословно — иначе задание решается копированием |
| Время генерации 10 сценариев | ≤ 10 мин на CPU, ≤ 1 мин на GPU | Замер на целевом железе |
| Отказоустойчивость | при недоступном сайдкаре — откат на рекомбинацию, 0 ошибок пользователю | Интеграционный тест с выключенным сайдкаром |

### 5.9 Персональный разбор (LLM, п. 2.9)

| Метрика | Порог | Проверка |
|---|---|---|
| Фактическая точность | 100 % упомянутых ошибок присутствуют в `issues` | Автопроверка: числа и коды из текста сверяются со структурой |
| Отсутствие выдуманных рекомендаций | 0 советов, противоречащих памятке ДДС | Выборочная проверка преподавателем, чек-лист |
| Полезность | оценка преподавателя/обучающегося по 5-балльной шкале, ≥ 4 | Кнопка «полезно / нет» под разбором |
| Время до появления разбора | ≤ 2 мин после завершения сессии (p95) | Метрика очереди задач |
| Деградация | при недоступной модели показывается правиловый текст | Интеграционный тест |

### 5.10 Распознавание доклада (Vosk, п. 2.10)

| Метрика | Порог | Проверка |
|---|---|---|
| WER на докладах | ≤ 25 % | Записанные эталонные доклады с расшифровкой |
| Полнота слотов | recall ≥ 0.8 по адресу, типу, силам | Размеченные записи |
| Реальное время | RTF ≤ 0.5 на ядро | Бенчмарк |
| Одновременных потоков | ≥ 10 без деградации | Нагрузочный тест |

## 6. Сквозные технические метрики для всего слоя моделей

Относятся к любому из инструментов §5 — то, что стоит собирать единообразно.

| Метрика | Зачем |
|---|---|
| Доступность инструмента (uptime) | Оценка не должна падать из-за модели: fallback обязателен |
| Доля срабатываний fallback | Если 30 % оценок посчитаны правилами, «ИИ» существует только на бумаге |
| Задержка p50 / p95 / p99 по инструменту | p99 важнее среднего: он определяет, успеет ли разбор к концу занятия |
| Длина очереди фоновых задач | Пик в конце занятия — 30 сессий одновременно |
| Версия модели и справочника в каждой оценке | Без этого нельзя сравнивать результаты между занятиями и объяснить расхождение |
| Дрейф распределения баллов | Резкий сдвиг среднего после обновления модели — сигнал регресса |
| Потребление RAM и CPU в пике | Ограничение офисного сервера |
| Размер артефактов модели | Локальная поставка: всё должно влезать в образ или том |

## 7. Что можно проверить и чем

### 7.1 Проверяется автоматически в CI

| Что | Как |
|---|---|
| Детерминированность оценки | Один и тот же снимок сессии → идентичная оценка. Юнит-тест, защищает от случайности в правилах |
| Границы шкал | Property-тест: любой критерий ∈ [0, 100], итог ∈ [0, 100], при пустых данных не NaN |
| Веса режимов | Сумма весов = 100 для обоих режимов; тест на `AssessmentWeights` |
| Пересчёт итога преподавателем | Нормировка весов при частичных правках — есть `AssessmentWeights.total`, покрыть краевыми случаями |
| Золотой набор сценариев | 20 эталонных прохождений («идеальное», «типовые ошибки», «ничего не сделал») с зафиксированными ожидаемыми баллами. Регрессионный тест при любой правке оценщика |
| Метрики моделей на фиксированных выборках | §5: accuracy, F1, MAE — как тесты с порогами, падают при регрессе |
| Отсутствие утечки эталона | `expectedAddress` и `expectedIncidentTypes` не должны появляться в ответах API обучающемуся вне `hints` в TRAINING |
| Непрерывность `realtime_event` | SQL-проверка `sequence_number` без разрывов |

### 7.2 Проверяется нагрузочно

| Что | Сценарий |
|---|---|
| Отклик ≤ 2 с при 100 пользователях | k6/Gatling: 100 виртуальных пользователей, профиль реального занятия (patch раз в 5–10 с, save раз в 2–3 мин) |
| 30 одновременных сессий в классе | Отдельный прогон с WebSocket-подключениями |
| Пик завершения | 30 сессий завершаются в течение минуты → очередь разбирается за ≤ 2 мин |
| Планировщик `detectOverdue` | Раз в секунду по всем сессиям: замер длительности тика при 100 сессиях, не должен приближаться к 1 с |
| Восстановление после рестарта | Перезапуск с 30 активными сессиями, проверка полного восстановления состояния |

### 7.3 Проверяется с участием людей

| Что | Как |
|---|---|
| Согласие ИИ и преподавателя | Преподаватель независимо оценивает 30 сессий, сравниваем с ИИ: MAE, корреляция, κ по критериям |
| Понятность фидбека | 5–7 обучающихся: «объясните своими словами, что вам нужно исправить» — по результату экрана |
| Полезность для преподавателя | Замер времени на разбор занятия с системой и без |
| Реалистичность сценариев | Действующий оператор/диспетчер оценивает выборку сгенерированных сценариев |
| Соответствие памятке ДДС | Сверка правил оценки с [materials/dds-workflow.md](../materials/dds-workflow.md) построчно |

### 7.4 Чего проверить нельзя и что с этим делать

| Ограничение | Как обойти |
|---|---|
| Нет эталонной методики оценки — заказчик её не имеет (Q&A) | Единственный доступный эталон — мнение преподавателя. Значит, метрика согласия с преподавателем важнее любой внутренней |
| Мало данных на старте: 96 сценариев, ноль проведённых занятий | Синтетические прогоны для технических метрик; учебные метрики честно помечать «недостаточно данных» вместо показа ложных цифр |
| Перенос навыка в реальную работу не измерим в тренажёре | Не заявлять этого. Максимум — удержание навыка между тренировкой и зачётом (§4.1) |
| Классы несбалансированы (GAS — 2 сценария) | Macro-F1 вместо accuracy; не обещать качество по редким типам |

## 8. Минимальный набор для старта

Если внедрять по одной метрике за раз, порядок такой — каждая следующая опирается на предыдущую.

1. **Таблица issues** ⚙ (разложить `ai_payload.issues` в строки) — открывает §2.1, §3.2 и половину §4 без единой модели.
2. **Поле в `draft.updated`** ⚙ — открывает временной анализ §2.2 и §5.5.
3. **Расхождение ИИ и преподавателя** — главная метрика успешности §4.2, считается сразу по существующим данным.
4. **Золотой набор прохождений** (§7.1) — страховка от регресса при всех дальнейших правках оценщика.
5. **Нагрузочный профиль занятия** (§7.2) — требование ТЗ, проверяется до, а не после защиты.
6. Дальше — технические метрики §5 по мере внедрения инструментов из роадмапа.
