# Где заменить правила на модели: дорожная карта оценки и генерации

Продолжение [ASSESSMENT_AND_SCENARIOS.md](ASSESSMENT_AND_SCENARIOS.md) («как есть»). Здесь — что из правиловой оценки стоит заменить моделью, более совершенным алгоритмом или временны́м анализом, чтобы оценка стала объективнее, фидбек обучающемуся — информативнее, а преподавателю — понятнее. Каждое предложение оценено по нагрузке и привязано к месту в коде.

Первоисточники ограничений: [materials/q-and-a.md](../materials/q-and-a.md) §1, §8, §13, §17, «Время отклика без GPU»; [materials/task-spec.md](../materials/task-spec.md), раздел «Производительность».

---

## 1. Ограничения, из которых исходим

| Ограничение | Что это значит для решений |
|---|---|
| Только локальный контур, без интернета в классе | Никаких облачных API. Модель можно **обучить** в облаке, но **работать** она должна локально |
| Сервер ориентирован на CPU; «стандартную современную видеокарту» можно закупить под обоснованное решение | По умолчанию — CPU. GPU допустима, но её надо обосновать конкретной функцией |
| ПК обучающихся — офисные, только браузер | На клиенте ничего не считаем; всё серверное |
| Класс 20–30 человек, целевая нагрузка 100, отклик интерфейса ≤ 2 с | Инференс не должен масштабироваться линейно с числом активных сессий в реальном времени |
| Норматив 30 с на реакцию, 3 мин на карточку | На пути «вызов → карточка → сохранить» модель не вызываем — прямая рекомендация заказчика |
| «Обучение и дообучение минутами — нормально» | Всё тяжёлое — при завершении сессии (асинхронно) или офлайн по кнопке преподавателя |
| Приоритет преподавателя абсолютен; его правки должны дообучать модель | Любая модель должна быть калибруема по правкам преподавателя и объяснима |
| «Сложная модель с кучей параметров, которую трудно поддерживать — плохо» | Предпочитаем прозрачные алгоритмы; LLM — только там, где без неё нельзя |

**Принцип:** три уровня вычислений.

1. **Онлайн (мс)** — только справочники и SQL: то, что можно звать при каждом `PATCH` черновика.
2. **При завершении сессии (секунды, асинхронно)** — малые модели на CPU: `complete()` записывает правиловую оценку сразу, обогащение приходит событием `assessment.updated` через секунды.
3. **Офлайн по кнопке (минуты)** — LLM, переобучение, пересчёт сложности.

## 2. Предложения по местам

### 2.1 Адрес: справочник улиц + нечёткий поиск вместо Левенштейна

**Сейчас.** [`AddressMatcher`](../../src/main/java/ru/lct/arm112/service/assessment/AddressMatcher.java): нормализация строк, Левенштейн ≤ 2 → «опечатка» (−40), иначе «другая улица» (−60). Ключевой кейс заказчика — «Дубнинская / Дубининская» — **обе улицы существуют**. Сейчас это трактуется как опечатка, хотя это именно неверная улица: службы уедут не туда.

**Предложение.**
- Локальный справочник улиц Москвы (выгрузка ГАР/ФИАС или OSM) в Postgres, индекс `pg_trgm`.
- Три исхода вместо двух: *существующая другая улица* (CRITICAL, −60), *несуществующее написание, близкое к одной реальной улице* (опечатка, −40), *правильно*.
- Автодополнение адреса в форме оператора 112 — как в реальном АРМ-112. Даёт и реализм, и объективный признак: «выбрал из справочника / набрал вручную».
- Нормализация через справочник закрывает сокращения («пр-т», «б-р») лучше, чем текущий regex в `TextUtil.normalize`.

**Нагрузка.** Миллисекунды, чистый SQL. Годится и для онлайна (автодополнение), и для оценки.

**Код.** `AddressMatcher.score`, новый `AddressReferenceService` + миграция со справочником, эндпоинт `GET /references/addresses?q=` для автодополнения.

### 2.2 Тип происшествия: иерархическая близость + классификатор по тексту

**Сейчас.** Жаккар по id типов ([`CardFillAssessor`](../../src/main/java/ru/lct/arm112/service/assessment/CardFillAssessor.java)): `fire.garbage` vs `fire.building` и vs `medical.*` — одинаково 0. Подсказка в TRAINING говорит только «не соответствует».

**Предложение.**
- Без ML: частичный балл за совпадение категории (`IncidentType.category`) — расстояние по дереву классификатора. Ошибка внутри категории — половина балла, между категориями — 0.
- ML: классификатор `callerText → тип` на эмбеддингах `rubert-tiny2` (≈29M параметров) + логистическая регрессия/kNN. Обучающая выборка: 96 билетов + синонимы из [`seed/incident-types.json`](../../src/main/resources/seed/incident-types.json); дообучение на сценариях, подтверждённых преподавателем (`referenceConfirmed`).
- Инференс через ONNX Runtime **внутри JVM** — без Python-сайдкара.

**Применение.**
1. Автоподбор эталона типов и служб для сгенерированных и ручных сценариев (сейчас у ручных службы считаются по ЕКП, а типы преподаватель вводит сам).
2. Объяснение обучающемуся: атрибуция слов вводной к типу («горит контейнер» → «Возгорание мусора») в `AssessmentIssue.message`.
3. Подсказка в `TRAINING` через `hints`: «по тексту заявителя похоже на …» — только для тренировки, не для зачёта.
4. Уверенность классификатора — признак сложности сценария (см. 2.6).

**Нагрузка.** ~10 мс на текст на CPU, ~0.5 ГБ RAM под модель. Звать при завершении сессии и при сохранении сценария преподавателем.

**Код.** `CardFillAssessor` (тип), `CardFillAssessor.hints`, `ScenarioService.create/generate`, новый `IncidentTypeClassifier`.

### 2.3 Грамотность: LanguageTool вместо регулярных выражений

**Сейчас.** [`LanguageChecker`](../../src/main/java/ru/lct/arm112/service/assessment/LanguageChecker.java): пять эвристик (смешанный алфавит, тройная буква, Левенштейн-1 к топониму, пунктуация, нет заглавных). −15 за находку.

**Предложение.** LanguageTool — Java-библиотека, встраивается в Spring Boot как зависимость, работает офлайн. Даёт орфографию, пунктуацию, согласование, с текстом объяснения и предложением замены по каждой ошибке — это и есть объективный фидбек вместо «небрежная пунктуация (2)».
- Пользовательский словарь топонимов и служебных терминов из сценариев и справочников (иначе ошибками станут улицы и «ДДС»).
- Сохранить существующую проверку «опечатка в топониме» — она специфична и полезна.
- Разделять вес: орфографическая ошибка в адресе/описании — тяжелее, чем пропущенная запятая.

**Нагрузка.** 100–300 мс на текст, 1–2 ГБ RAM (держать одну инстанцию `JLanguageTool`, не создавать на запрос). 30 обучающихся × 5 карточек = 150 проверок за занятие — секунды суммарно. Только при завершении сессии.

**Код.** Замена реализации `LanguageChecker.check`; интерфейс и `Result` сохраняются.

### 2.4 Коммуникация в ДДС: содержание комментария, а не длина

**Сейчас.** [`CardActionsAssessor`](../../src/main/java/ru/lct/arm112/service/assessment/CardActionsAssessor.java): комментарий короче 15 символов — −30. Обходится словами «передано в службу».

**Предложение.** Памятка ДДС требует в комментарии *основание* и *результат*.
- Шаг 1 (без ML): слотовая проверка — есть ли *адресат* (служба, должность, из справочника), *действие* (словарь глаголов: передано, направлено, выехали, устранено…), *основание* (код причины или его словесный эквивалент). Каждый отсутствующий слот — отдельный issue с понятной формулировкой.
- Шаг 2: преподаватель уже выставляет балл по критерию `communication` в `LessonService.assess` — это готовая разметка. После нескольких занятий обучить классификатор «полный / неполный комментарий» на эмбеддингах из 2.2. Это самая простая форма «дообучения от действий преподавателя», которую просил заказчик.

**Нагрузка.** Миллисекунды. При завершении сессии.

**Код.** `CardActionsAssessor` (блок коммуникации), новый `CommentSlotChecker`; данные — `assessment.teacher_criteria`.

### 2.5 Временной анализ: траектория вместо одного порога

**Сейчас.** Время в CARD_FILL — `savedAt − startedAt` против 3 минут; в CARD_ACTIONS — два липких флага просрочки. Всё, что между стартом и сохранением, теряется, хотя каждый `PATCH /card-drafts/{id}` проходит через сервер (`publishDraft(… "draft.updated")`).

**Предложение.**
- Писать таймстемпы по полям в `CardFillService.patch`: первый ввод адреса, первый выбор типа, каждая смена типа, каждое изменение служб, паузы > 20 с. Хранить в снимке сессии (`TrainingStateStore`).
- Метрики: время до адреса, время до типа, порядок («сначала адрес и тип, подробности — в описание» — это уже есть в рекомендациях, но не измеряется), число смен типа (колебания), доля времени в бездействии.
- **Групповые нормы** вместо жёсткого порога: перцентиль по группе/потоку («медленнее 80 % группы по вводу адреса»). Норматив 3 минуты остаётся как абсолют, перцентиль — как относительная оценка.
- **Прокликивание** в ДДС: интервалы между статусами реагирования. «Прибытие» через 2 с после «Начало реагирования» — имитация работы без чтения карточки. Минимально правдоподобные интервалы задаются в настройках (`SettingsService`), нарушение — issue `CLICK_THROUGH`.
- **Кривая обучения**: по завершённым сессиям обучающегося — тренд времени и балла по номеру сессии. Это и есть «адаптация под уровень» из Q&A §4, без модели.

**Нагрузка.** Нулевая: несколько SQL-запросов при завершении сессии и при открытии отчёта.

**Код.** `CardFillService.patch`, `TrainingStateStore` (поля траектории), `CardFillAssessor`/`CardActionsAssessor` (новые issue), новый `AnalyticsService`, отчёт занятия и экран результатов.

### 2.6 Сложность сценария: эмпирическая (Rasch/IRT) вместо ручной цифры

**Сейчас.** `Scenario.difficulty` ставится вручную, ни на что не влияет. Заказчик просил, чтобы ИИ **сам предлагал вес 1–10** для сгенерированного задания.

**Предложение.**
- Эмпирическая сложность: однопараметрическая модель Раша по матрице «обучающийся × сценарий → балл» из таблицы `assessment` (через `CardDraft.scenarioId` / `CardState.scenarioId`). При 30 × 20 наблюдений считается за миллисекунды; даёт и сложность сценария, и способность обучающегося на одной шкале.
- Для сценариев без истории — регрессия по признакам: число ожидаемых служб, есть ли формальный адрес или только ориентир (`addressClarified`), `expectedDecision = DECLINE`, число типов, уверенность классификатора из 2.2.
- Дальше: взвешивать рейтинг в `RatingService` по сложности; преподавателю показывать «предложено ИИ: 7, подтвердить/изменить».

**Нагрузка.** Ночной пересчёт или по кнопке; миллисекунды.

**Код.** Новый `DifficultyService`, `ScenarioService.generate` (предложение веса), `RatingService`.

### 2.7 Калибровка ИИ по правкам преподавателя

**Сейчас.** `LessonService.assess` сохраняет пары «балл ИИ / балл преподавателя» по критериям (`assessment.teacher_criteria`), но ничего с ними не делает.

**Предложение.**
- Изотоническая или линейная калибровка на критерий: ИИ-балл → ожидаемый балл преподавателя.
- Подгонка весов `AssessmentWeights` по итогам преподавателя (МНК с ограничениями: веса ≥ 0, сумма 100). Показывать преподавателю «текущие веса, предложенные по вашим оценкам» — применять только после подтверждения.
- Экран расхождений «ИИ vs преподаватель» по критериям и по обучающимся — прозрачно, без модели.

Это прямая реализация «дообучение от действий преподавателя, приоритет всегда за преподавателем» в понятном виде.

**Нагрузка.** Миллисекунды, по кнопке или ночью.

**Код.** `LessonService.assess`, `AssessmentWeights` (веса из БД вместо констант), новый `CalibrationService`.

### 2.8 Генерация сценариев: LLM офлайн вместо рекомбинации

**Сейчас.** [`ScenarioService.generate`](../../src/main/java/ru/lct/arm112/service/ScenarioService.java) склеивает ситуацию одного билета с адресом другого внутри категории. Получаются несуразности («подъезд» на железнодорожном переезде), нет предложения сложности, нет личности заявителя.

**Два пути, оба совместимы с контуром.**

1. **Банк, сгенерированный заранее** (рекомендованный заказчиком подход). В облаке (это разрешено) генерируется большой набор по категориям, затем **структурная валидация**: тип из классификатора, адрес из справочника (2.1), службы по ЕКП, обязательные поля. Шипится с приложением как `seed/generated.json`; преподаватель подтверждает через `confirm-reference`.
2. **Локальная модель по кнопке.** Qwen2.5-7B-Instruct (Q4) через llama.cpp/Ollama-сайдкар в compose, structured output по JSON-схеме `ScenarioUpsert`, та же валидация. Генерация — фоновая задача с очередью и статусом; результат появляется в библиотеке как `GENERATED`, `referenceConfirmed = false`.

**Защита от галлюцинаций.** Не доверие модели, а фильтр: сценарий не попадает в библиотеку, если адрес не найден в справочнике, тип не из классификатора, службы не соответствуют ЕКП. Плюс обязательное подтверждение преподавателя — как заказчик и предложил.

**Нагрузка.** На CPU 7B Q4 — 5–10 ток/с; сценарий ≈ 300 токенов ≈ 30–60 с; 10 сценариев — 5–10 минут в фоне. Допустимо («минуты — нормально»). С GPU класса RTX 4070 12 ГБ — вся пачка под минуту. **Это единственное обоснование закупки видеокарты в проекте.**

**Код.** `ScenarioService.generate` → постановка задачи, новый `GenerationJobService` + сайдкар в `compose.*.yaml`, эндпоинт статуса задачи.

### 2.9 Персональный разбор для обучающегося

**Сейчас.** Фиксированные строки в `recommendations`.

**Предложение.** Та же локальная LLM пишет 5–8 предложений по **структурированному** входу — `issues` и баллы по критериям, не по сырым данным (меньше поводов для галлюцинаций). Один вызов на сессию при завершении, через очередь. Пока текст готовится, показывается правиловый вариант; готовый приходит событием `assessment.updated`.

Для преподавателя — сводка по занятию без LLM: группировка `issues` по коду («12 из 30 ошиблись в улице у сценария X») — это SQL.

**Нагрузка.** Пик — 30 сессий завершаются в одну минуту в конце занятия. На CPU 3B-модель отдаст всё за ~5 мин, 7B — 10+ мин; с GPU — меньше минуты. Без GPU — только 3B или отложить.

**Код.** `TrainingEngine.complete` → постановка задачи после `assessmentRepo.insert`, новый `DebriefService`, поле `debrief` в `Assessment`.

### 2.10 Голосовой доклад руководителю (опционально, последним)

**Сейчас.** Исходящий звонок — только смена состояний `DIALING → RINGING → CONNECTED → ACKNOWLEDGED`; содержание доклада не оценивается.

**Предложение.** Единственный голос, который заказчик оставил в задаче, — диалог ДДС → руководитель. Vosk (русская малая модель ≈ 50 МБ, CPU, реальное время) распознаёт доклад, дальше — слотовая проверка покрытия (адрес, тип, силы и средства, статус) как в 2.4.

**Нагрузка.** Потоковое распознавание ≈ 0.3 реального времени на ядро; 30 одновременных докладов потребуют 8–10 ядер только под это. Доклады короткие и не синхронные, но это единственный пункт с инференсом **во время** занятия — средний риск, делать последним и с лимитом одновременных потоков.

|---|---|---|---|---|---|---|

| 2.5 | Временная траектория, прокликивание, перцентили, кривая обучения | Postgres | оценка, отчёт | мс | Объективный фидбек по времени; ловит имитацию | **2** |

| 2.2 | Иерархия типов + `rubert-tiny2` (ONNX в JVM) | +0.5 ГБ RAM | оценка, сохранение сценария | 10 мс/текст | Частичный балл, объяснение «почему», автоэталон | 4 |

| 2.9 | LLM-разбор для обучающегося | как 2.8 | завершение сессии, очередь | 1–10 мин на пик | Персональный фидбек | 8 |

**Выводы.**
- Пункты 2.1–2.7 работают на любом офисном сервере без GPU, не трогают путь 30 секунд и покрывают большую часть требований Q&A (сложность через веса, дообучение от преподавателя, объективность по времени и правильности).
- Пункты 2.8–2.9 — единственное, что оправдывает видеокарту. Без неё их можно оставить в режиме «офлайн-банк + фоновая очередь на CPU».
- На ПК обучающегося ничего не меняется: всё серверное, браузеру достаточно.

## 4. Архитектурные точки

- **Один процесс, где можно.** LanguageTool и ONNX Runtime живут в JVM — не нужен Python-сайдкар, не усложняется деплой ([DEPLOYMENT.md](../DEPLOYMENT.md)).
- **Сайдкар только для LLM** (llama.cpp/Ollama) в `compose.production.yaml`, с профилем, чтобы разворачивать по желанию; приложение работает и без него (генерация — рекомбинацией, разбор — правиловый).
- **Очередь фоновых задач** в Postgres (таблица `job`), без брокера: генерация, разбор, пересчёт сложности и калибровки. Статус — через существующие события `EventService`.
- **Обогащение, а не замена.** `complete()` по-прежнему пишет правиловую оценку синхронно; модели дописывают issues/тексты позже событием `assessment.updated`. Если сайдкар недоступен — обучающийся всё равно получает результат.
- **Настройки точности** (`SettingsService`): пороги слотов, минимальные интервалы прокликивания, включение/выключение каждого обогащения — заказчик прямо сказал, что «точность настраиваемая».

## 5. Порядок внедрения

1. Справочник адресов и трёхуровневая оценка улицы (2.1) — меняет главный критерий с весом 40.
2. Таймстемпы по полям и прокликивание (2.5) — данные начинают копиться сразу, аналитика достраивается позже.
3. LanguageTool (2.3).
4. Иерархическая близость типов (часть 2.2 без ML) и слоты комментариев (часть 2.4 без ML).
5. `rubert-tiny2` в JVM: автоэталон, объяснение, подсказки (2.2), затем классификатор комментариев (2.4) на накопленных оценках преподавателя.
6. Rasch-сложность и калибровка (2.6, 2.7) — когда есть 2–3 проведённых занятия.
7. Банк сценариев из облака (2.8, путь 1); локальная LLM и разбор (2.8 путь 2, 2.9) — при наличии GPU.
8. Голосовой доклад (2.10) — при подтверждённом запросе заказчика.
