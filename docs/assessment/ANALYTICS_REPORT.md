# Аналитика: что сделано, как поддерживается, что измерено

Отчёт на 2026-09-27, дополнен после устранения найденного узкого места (§4.6). Все числа получены прогонами на развёрнутом стенде (собранный образ, PostgreSQL 17 в Docker) и лежат в `benchmarks/`. Там, где число взято из более раннего замера, это сказано.

---

## 1. Что сделано

Аналитика — это пять расчётных узлов, четыре экранных ручки и три таблицы, куда складываются исходные данные. Ничего из этого не считается «на лету при показе»: тяжёлое пишется в момент оценивания, экраны только выбирают и сводят.

### 1.1 Расчётные узлы

| Узел | Строк | Что делает | Когда работает |
|---|---:|---|---|
| `IncidentTypeClassifier` | 307 | подбирает тип происшествия по тексту заявителя | **во время оценивания** и при проверке сгенерированной вводной |
| `RaschService` | 272 | эмпирическая сложность сценария и способность обучающегося на одной шкале (JMLE) | по запросу экрана |
| `CalibrationService` | 175 | линейная калибровка оценки ИИ по правкам преподавателя | по запросу экрана |
| `TimingAnalyticsService` | 91 | куда ушло время внутри карточки и как это на фоне группы | по запросу экрана |
| `DashboardService` | 285 | сводит всё перечисленное в то, что показывает один экран | по запросу экрана |

Итого 1130 строк. Логики оценивания в `DashboardService` нет — только выборка и приведение к виду для интерфейса.

### 1.2 Ручки

```
GET /api/v1/teacher/lessons/{id}/overview      обзор занятия
GET /api/v1/teacher/trainees/{id}/profile      профиль обучающегося
GET /api/v1/teacher/scenarios/quality          качество библиотеки (Раш)
GET /api/v1/teacher/calibration                расхождение ИИ и преподавателя
GET /api/v1/assessments/{id}/debrief           персональный разбор
```

### 1.3 Где хранятся исходные данные

| Таблица | Миграция | Зачем аналитике |
|---|---|---|
| `assessment_issue` | `V9` | типовые ошибки занятия, устойчивые недочёты обучающегося |
| `assessment_card` | `V10` | матрица «обучающийся × сценарий» — без неё Раш не построить |
| `assessment_debrief` | `V14` | текст персонального разбора, посчитанный в фоне |

Сессионного балла для Раша не хватает: он усредняет разные сценарии в одно число. Поэтому заведена запись по каждой карточке.

## 2. Схема: где аналитика включается и что делает

```
ЗАНЯТИЕ ИДЁТ
│
├─ обучающийся заполняет карточку
│     │
│     └─► IncidentTypeClassifier ──► подсказка типа происшествия
│           (по тексту заявителя, синонимы + стемминг)
│
│     движок пишет траекторию правок: какое поле, когда, сколько раз
│     └─► training_state.trajectories        ← сырьё для временного анализа
│
▼
СЕССИЯ ЗАВЕРШЕНА  ──────────────────────────────── синхронно, ~20–30 мс
│
├─ CardFillAssessor / CardActionsAssessor
│     ├─ адрес, классификация, службы, время, грамотность
│     └─ IncidentTypeClassifier ──► зачёт «верная категория, неверный тип»
│
├─► assessment           итог и баллы по критериям
├─► assessment_issue     замечания с кодом, эталоном и введённым
├─► assessment_card      баллы по каждой карточке ← матрица для Раша
│
└─► job (SESSION_DEBRIEF)   задача в очередь
      │
      ▼
ФОНОВАЯ ОЧЕРЕДЬ ─────────────────────────────────── асинхронно
│
└─ DebriefHandler
      ├─ собирает структуру замечаний
      ├─ текст: правила или языковая модель
      ├─ RussianTextGuard ──► чужая письменность не покажется обучающемуся
      └─► assessment_debrief

▼
ПРЕПОДАВАТЕЛЬ ОТКРЫВАЕТ ЭКРАН ───────────────────── по запросу
│
└─ DashboardService
      ├─ SQL-агрегаты по assessment / assessment_issue / assessment_card
      ├─ RaschService          ──► сложность сценариев (от 10 наблюдений)
      ├─ CalibrationService    ──► калибровка (от 30 пар на критерий)
      └─ TimingAnalyticsService ─► перцентиль времени (от 8 человек в группе)
```

**Три порога, ниже которых узел молчит, а не выдумывает:**

- `RaschService.MIN_OBSERVATIONS = 10` — сценарий с меньшим числом наблюдений в выдачу не попадает;
- `CalibrationService.MIN_PAIRS = 30` — критерий без тридцати правок преподавателя уходит в `skipped` с объяснением;
- `TimingAnalyticsService.MIN_GROUP = 8` — на группе меньше восьми перцентиль не выдаётся: ранг там шум, один отсутствующий меняет картину целиком.

Это сделано намеренно. Пустой экран, выглядящий рабочим, вводит в заблуждение сильнее ошибки.

## 3. Как это поддерживается

### 3.1 Регрессия оценки

**15 эталонных прогонов занятия** (`GoldenRunHarness`) с заранее посчитанным ожидаемым результатом по каждому критерию и списком замечаний. В строгом режиме (`-Dgolden.strict=true`) расхождение с эталоном роняет сборку.

Набор нашёл четыре дефекта раньше пользователей: самоналоженный штраф за пунктуацию, зависание сессии в режиме «по одной», поломку резервной копии на новых таблицах (дважды) и ухудшение MAE калибровкой там, где ИИ и так согласен с преподавателем.

За три сегодняшних слияния (`main`, ветка надёжности, ветка экранов) набор отработал трижды — **отклонение 0,0 по всем пятнадцати прогонам каждый раз**.

### 3.2 Индексы под запросы аналитики

```sql
idx_issue_lesson_code     assessment_issue (lesson_id, code)
idx_issue_trainee_code    assessment_issue (trainee_id, code, created_at)
idx_card_scenario         assessment_card (scenario_id, trainee_id)
idx_card_trainee          assessment_card (trainee_id, created_at)
idx_card_lesson           assessment_card (lesson_id)
idx_assessment_session    assessment (session_id)
idx_session_lesson        training_session (lesson_id)
```

### 3.3 Резервное копирование

`BackupTablesTest` сверяет список таблиц выгрузки со схемой. Проверка заведена после того, как копия дважды сломалась на новых таблицах — теперь новая таблица без правки списка не пройдёт сборку.

### 3.4 Отдельные проверки узлов

`IncidentTypeClassifierTest`, `DashboardEndpointsTest` (сквозная: занятие проводится целиком, затем дёргаются все ручки и проверяется **осмысленность** выдачи, а не только код ответа), `DebriefTest`, `ScenarioValidatorTest`, `JobQueueTest`, `BackupTablesTest`.

### 4.5 Сколько наблюдений и сколько прогонов нужно на p95 и p99

Обзорная серия §4.2 сделана при семи повторах на ручку, и это её главный недостаток: **семь наблюдений не дают перцентиля.** Ранг оценки квантиля распределён биномиально с разбросом порядка `sqrt(n·q·(1−q))`, поэтому на малом `n` «p95» вырождается в максимум выборки.

| Квантиль | Минимум, чтобы число что-то значило (`n ≥ 10/(1−q)`) | Для устойчивой оценки (`n ≥ 100/(1−q)`) |
|---|---:|---:|
| p50 | 20 | 200 |
| p95 | **200** | 2000 |
| p99 | **1000** | 10 000 |

Замер параметризован: `-Danalytics.repeats` задаёт число повторов последовательной части, `-Danalytics.bursts` — сколько раз вся группа открывает разбор. В выдаче каждая строка помечена тем, что по ней можно утверждать: `p50 p95 p99`, `p50 p95, p99 шум`, `только p50`, `мало данных`.

**Настоящие перцентили на тысяче наблюдений** (`-Danalytics.repeats=1000`):

| Запрос | группа 30 |  |  | группа 100 |  |  |
|---|---:|---:|---:|---:|---:|---:|
| | p50 | p95 | p99 | p50 | p95 | p99 |
| Калибровка | 5 | 19 | 26 | 4 | 16 | 21 |
| Качество сценариев | 5 | 19 | 25 | 5 | 17 | 25 |
| Обзор занятия | 10 | 29 | 41 | 11 | 34 | 53 |
| Профиль обучающегося | 10 | 28 | 40 | 9 | 26 | 39 |
| **Отчёт занятия** | 42 | 81 | 110 | 151 | **249** | **384** |
| Результаты обучающегося | 29 | 102 | 168 | 74 | 201 | 218 |
| Рейтинг обучающегося | 20 | 59 | 96 | 52 | 119 | 178 |

Данные до правки: `benchmarks/analytics-30-users-deep-before-fix.csv`, `analytics-100-users-deep-before-fix.csv`. Файлы без суффикса — замеры после правки из §4.6.

Настоящий p95 оказался **ниже**, чем «p95» из обзорной таблицы: на группе 30 обзор занятия 29 мс против 83, отчёт 81 мс против 334. Максимум из семи наблюдений ловит выброс и выдаёт его за типичное худшее — то есть §4.2 завышала, а не занижала.

#### Сколько прогонов

Наблюдений внутри прогона теперь достаточно, но этого мало. Пять независимых прогонов на группе 30 при 300 повторах дали такой разброс p95:

| Запрос | П1 | П2 | П3 | П4 | П5 | разброс |
|---|---:|---:|---:|---:|---:|---|
| Обзор занятия | 42 | 25 | 38 | 69 | 72 | 47 мс (**96 %**) |
| Профиль обучающегося | 34 | 24 | 40 | 61 | 65 | 41 мс (**92 %**) |
| Отчёт занятия | 149 | 97 | 216 | 342 | 407 | 310 мс (**128 %**) |
| Калибровка | 19 | 16 | 18 | 35 | 29 | 19 мс (81 %) |

**Разброс между прогонами больше любой ошибки выборки внутри прогона.** И он не случаен: значения растут почти монотонно от первого прогона к пятому.

Причина найдена проверкой, а не рассуждением. Каждый прогон дописывает в базу группу, занятие и оценки; за пять прогонов база выросла с 130 до 281 обучающегося и с 2 до 7 занятий. Три прогона, каждый на **свежей базе**, дают совсем другую картину:

| Запрос | Ч1 | Ч2 | Ч3 | разброс |
|---|---:|---:|---:|---|
| Обзор занятия | 16 | 15 | 13 | 3 мс (20 %) |
| Профиль обучающегося | 15 | 14 | 13 | 2 мс (14 %) |
| Отчёт занятия | 42 | 39 | 36 | 6 мс (15 %) |
| Калибровка | 8 | 8 | 8 | 0 мс (**0 %**) |

Разброс упал с 81–128 % до 0–20 %. Значит колебания давала не измерительная погрешность, а **наполнение базы**.

#### Что из этого следует для методики

1. **Внутри прогона:** 1000 повторов, если нужен p99; 200, если достаточно p95. Обзорные семь повторов годятся только на медиану.
2. **Число прогонов:** трёх достаточно, **но только если каждый идёт на одинаковом состоянии базы**. Наращивать прогоны на растущей базе бессмысленно — они меряют разные системы.
3. **Что именно объявлять:** медиану p95 по прогонам и разброс рядом. Одно число без разброса на этих данных вводит в заблуждение вдвое.
4. **Отдельно стоит мерить зависимость от объёма базы** — по §4.5 видно, что это более сильный фактор, чем размер группы. Причина этой зависимости найдена и устранена, см. §4.6; после правки дрейфа нет.

### 4.6 Найденная и устранённая причина роста

Разброс из §4.5 оказался не свойством системы, а одним дефектом.

`LessonService.report` вызывал `RatingService.traineeRating` **в цикле по каждому обучающемуся занятия**, а тот начинал с `load()` — выборки **всех оценок в базе без единого условия отбора**. Один отчёт по группе из тридцати человек означал тридцать полных проходов по таблице оценок. Стоимость росла как «размер группы × вся история центра», и именно это давало и рост p95 от прогона к прогону, и рост от 94 мс на группе 10 до 652 мс на группе 100.

Индексом это не лечилось: запрос ничего не фильтровал намеренно.

**Что сделано.** Условие отбора перенесено в SQL (по группе, по обучающемуся или по занятию), добавлен `RatingService.ratingsOf` — один запрос на группу вместо одного на обучающегося. Профиль обучающегося тоже задействовал этот вызов и выиграл заодно.

**Результат, пять прогонов подряд на одном стенде** (группа 30, 300 повторов):

| Запрос | до: p95 по прогонам | после: p95 по прогонам |
|---|---|---|
| Отчёт занятия | 149 · 97 · 216 · 342 · 407 → разброс **128 %** | 25 · 23 · 22 · 23 · 20 → разброс **22 %** |
| Обзор занятия | 42 · 25 · 38 · 69 · 72 → **96 %** | 13 · 13 · 11 · 12 · 11 → **17 %** |
| Профиль обучающегося | 34 · 24 · 40 · 61 · 65 → **92 %** | 13 · 10 · 10 · 11 · 9 → **38 %** |

Дрейф исчез: в серии «после» база росла так же (пять прогонов по тридцать человек), а значения остались плоскими. То есть убран именно член, зависевший от объёма базы, а не просто снижена константа.

**Перцентили на тысяче наблюдений, группа 100, после правки:**

| Запрос | p50 | p95 | p99 | было p95 |
|---|---:|---:|---:|---:|
| Калибровка | 3 | 5 | 6 | 16 |
| Качество сценариев | 4 | 6 | 7 | 17 |
| Обзор занятия | 11 | 13 | 16 | 34 |
| Профиль обучающегося | 7 | 9 | 11 | 26 |
| **Отчёт занятия** | 46 | **53** | 64 | **249** |
| Результаты обучающегося | 51 | 141 | 162 | 201 |
| Рейтинг обучающегося | 31 | 71 | 140 | 119 |

Отчёт занятия — с 249 до **53 мс**, почти впятеро. Худшее наблюдение по всей выдаче — 204 мс при нормативе 2000.

**Отдельной оптимизации базы не потребовалось.** Ни один индекс не добавлен: проблема была в числе запросов, а не в их плане.

### 4.7 Полное профилирование: все ручки чтения

После правки §4.6 профилирована **каждая значимая ручка чтения** — 22 штуки, по 200 обращений на каждую, на двух объёмах базы. Замер: `EndpointProfileTest`.

Смысл не в абсолютных миллисекундах, а в **отношении**. Ручка, выросшая вместе с базой, читает больше, чем ей нужно; на пустой базе полный проход по таблице неотличим от выборки по индексу, и абсолютная задержка такого не показывает.

#### Статический аудит

Полных проходов по таблице (`select` без условия отбора) в коде осталось **семь**, и все по мелким или служебным таблицам: три `count(*)` для постраничной выдачи, список групп, список настроек, список материалов в резервном копировании. Ни один не на пути экранов разбора.

Запросов внутри циклов найдено три содержательных:

| Место | Что делает | Оценка |
|---|---|---|
| `LessonService.monitor` | `users.findById` на каждую сессию | выборка по первичному ключу, N мелких запросов; монитор опрашивается во время занятия |
| `DashboardService.persistentIssues` | коррелированный подзапрос на каждый код замечания | число кодов ограничено сверху (~23) |
| `DashboardService.scenarioQuality` | `scenarios.findById` **и** `discrimination` на каждый сценарий | два запроса на сценарий, число сценариев растёт |

#### Динамический профиль

| Ручка | малая база | большая база | рост |
|---|---:|---:|---:|
| **teacher/scenarios/quality** | 8 | 69 | **8,6×** |
| trainee/results | 8 | 19 | 2,4× |
| teacher/scenarios | 26 | 54 | 2,1× |
| teacher/lessons/{id}/report | 15 | 25 | 1,7× |
| teacher/trainees/{id}/profile | 13 | 19 | 1,5× |
| teacher/lessons | 8 | 10 | 1,2× |
| остальные 16 ручек | 6–14 | 3–13 | 0,4–0,9× |

p95, мс. Малая база — 2 занятия на 10 человек; большая — 30 занятий на 20 человек, 50 вводных, 4833 карточки. Данные: `benchmarks/endpoints-small.csv`, `endpoints-rasch-wide.csv`.

Шестнадцать ручек из двадцати двух от объёма базы **не зависят вовсе** — их значения даже снизились за счёт прогрева. Отчёт по занятию после правки §4.6 растёт в 1,7 раза на пятнадцатикратном росте базы, то есть практически не растёт.

#### Единственная ручка с настоящим ростом

`teacher/scenarios/quality` — **8,6×**. Причина измерена, а не выведена:

| Сценариев в выдаче | Карточек в базе | p95 |
|---:|---:|---:|
| 0 | 2840 | 13 мс |
| 18 | 3640 | 44 мс |
| 33 | 4833 | 69 мс |

Зависимость линейна по числу сценариев, около **1,7 мс на сценарий**. На полной библиотеке в 111 вводных это даёт порядка 200 мс — до норматива далеко, но это единственное место, которое продолжает расти.

**Оговорка о методике, без которой числа выше врут.** Первые попытки профилирования показывали эту ручку плоской и дешёвой: 9 мс. Причина была в данных замера — все обучающиеся работали одинаково, модель Раша отбрасывает сценарий без разброса результатов, выдача была пуста, и цикл по сценариям не выполнялся ни разу. Пришлось научить замер заполнять карточку по эталону самой вводной, чтобы часть группы отработала верно. **Профиль на однородных данных показывал бы благополучие там, где его нет.**

#### Что из этого следует

Рост складывается из двух частей, и они разные по природе:

1. **Два запроса на сценарий** (`findById` и `discrimination`) — устранимы одной выборкой на всех. Это та же ошибка, что была в рейтинге, только меньшего масштаба.
2. **Полный проход по `assessment_card`** в `RaschService.estimate()` — **устранить нельзя**. Модель Раша оценивает сложность по всей матрице «обучающийся × сценарий»; по срезу её не посчитать. Здесь лечение другое: считать в фоновой очереди по расписанию и отдавать готовое, а не по запросу экрана.

Ни то ни другое не делалось: 69 мс при нормативе 2000 не требуют вмешательства сегодня. Но когда дойдёт — это ровно два разных приёма, и путать их не надо.

## 5. Синтетические прогоны и что они дали

Реальных пользователей на момент разработки нет, поэтому качество расчётных узлов проверялось на синтетике с **известным правильным ответом**: генерируется когорта с заданными способностями и сложностями, прогоняется через боевой API, затем проверяется, восстановил ли узел то, что было заложено.

### 5.1 Модель Раша — восстановление сложности

Когорта 24 обучающихся × 3 занятия × 4 карточки, пул из 10 сценариев, 288 карточек.

| Показатель | Результат |
|---|---|
| Сходимость | 9 итераций, 42 мс |
| Ранговая корреляция по сложности | **rho = 0,673** |
| Ранговая корреляция по способности | **rho = 0,603** |

Данные: `benchmarks/cohort-c1-rasch.csv`, `cohort-c1-abilities.csv`.

Два ограничения, которые прогон и выявил:

1. Совпадения в логитах ждать нельзя: «справился с карточкой» складывается из четырёх независимых испытаний со своими трудностями, поэтому эффективная сложность — монотонная функция заданной, но не равная ей.
2. **Раш считает способность постоянной, а она растёт.** Оценённое θ — среднее по всей истории, поэтому у быстро растущих текущую способность оно занижает. Для рейтинга это надо считать по окну последних занятий.

### 5.2 Калибровка по правкам преподавателя

Заложенные в когорту преобразования восстановлены почти точно (72 пары на критерий):

| Критерий | Наклон найден / заложен | MAE до | MAE после | Улучшение |
|---|---|---:|---:|---:|
| Адрес | 0,97 / 0,90 | 16,53 | 1,84 | **−88,9 %** |
| Время | 0,82 / 0,80 | 12,42 | 1,50 | **−87,9 %** |
| Грамотность | 1,03 / 1,10 | 11,78 | 2,25 | **−80,9 %** |

Данные: `benchmarks/cohort-c1-calibration.csv`.

**Отрицательный результат того же прогона:** на критериях, где ИИ и так согласен с преподавателем, калибровка **ухудшала** MAE (1,617 → 1,638). Подгонка к шуму. Отсюда порог `MIN_PAIRS = 30` и то, что калибровка выдаётся как *предложение*, а не применяется сама.

### 5.3 Классификатор типа происшествия

Измерено на 76 размеченных вводных: **top-1 = 65,8 %**, macro-F1 = 0,590. *Поправка 28.09: разметка была автоматической, теми же ключевыми словами; на ручной разметке 96 билетов top-1 = 36,5 %, top-3 = 56,3 %.*

**Главный отрицательный результат проекта.** В попытке улучшить качество было добавлено 54 синонима «про запас». Банк из 15 вводных продолжал проходить, а независимая мера на 76 билетах **рухнула с 65,8 % до 51,3 %**. Правка отменена, оставлены только пять действительно нужных синонимов. Случай разобран в [SYNONYMS_AUDIT.md](SYNONYMS_AUDIT.md) как пример переобучения на банк проверок.

Там же — почему не взята нейросетевая модель: в библиотеке 66 типов, размеченных вводных 76 штук и они покрывают 20 типов; у 46 типов нет ни одного примера. Модель на такой выборке уверенно предсказывала бы три частых класса и никогда — остальные, то есть была бы хуже бесполезной именно на редких происшествиях, где помощь и нужна.

### 5.4 Языковая модель для генерации и разбора

Замер на целевом железе без GPU. Ключевой результат: ограничение выборки **грамматикой GBNF** (только кириллица) подняло долю годных вводных **с 25 % до 100 %** на Qwen2.5-7B Q4. Это опровергло две собственные гипотезы — о влиянии квантования и о необходимости русскоязычного дообучения.

Данные: `benchmarks/llm-*.csv`, разбор — в [LLM_EXPERIMENT.md](LLM_EXPERIMENT.md).

## 6. Границы: что этими числами утверждать нельзя

| Можно утверждать | Нельзя утверждать |
|---|---|
| Экраны аналитики укладываются в норматив ТЗ до ста человек на этом стенде | Что так же будет на сервере заказчика: другое железо и другой диск |
| Агрегатные ручки почти не зависят от размера группы, растёт только отчёт | Что отчёт останется приемлемым на тысяче обучающихся |
| Раш и калибровка восстанавливают заложенные параметры на синтетике | Что они так же сработают на реальных обучающихся: поведение в когорте синтетическое |
| p95 и p99 из §4.6 — настоящие перцентили на тысяче наблюдений после правки | Что так же будет на библиотеке из ста вводных: измерено до 33 сценариев в выдаче, дальше — экстраполяция |
| Из 22 ручек чтения от объёма базы растёт одна (§4.7) | Что нет роста по другому измерению: менялись объём базы и число вводных, не длина истории одного обучающегося |
| Классификатор даёт 65,8 % top-1 на размеченных билетах | Что столько же будет на живой речи заявителя |

**Три технических оговорки к замерам выше:**

1. **Экземпляр прогрет.** Серия из восемнадцати прогонов шла по одному и тому же поднятому стенду. Первая оценка после старта стоит дороже — инициализация проверки грамотности; это видно в §4.1.
2. **База росла по ходу серии.** Каждый замер добавляет в неё группу и занятие. Это смещает оценку **в пессимистичную сторону** — для вопроса о запасе прочности направление верное. Насколько сильно смещает, измерено отдельно в §4.5: на растущей базе разброс p95 между прогонами достигал 128 %, на свежей — не превышал 20 %.
3. **Первый заход серии пришлось выбросить.** В самом замере карта задержек не была потокобезопасной: из десятков потоков `LinkedHashMap` портилась, и в выдаче появлялась одна и та же строка дважды. Исправлено на `ConcurrentHashMap`, вся серия пересчитана — в отчёте числа из повторного прогона.

## 7. Как повторить

```bash
# отдельный стек, чтобы не трогать демонстрационный стенд
POSTGRES_PORT=55436 BACKEND_PORT=8082 docker compose -p arm112-bench up -d postgres backend

# экраны аналитики по размеру группы
for N in 10 15 20 25 30 40 50 60 100; do
  mvn test -Dtest=AnalyticsLoadTest -Dload.url=http://localhost:8082 -Danalytics.users=$N
done

# нагрузка самого занятия
for N in 10 15 20 25 30 40 50 60 100; do
  mvn test -Dtest=LoadProfileTest -Dload.url=http://localhost:8082 -Dload.users=$N
done

docker compose -p arm112-bench down -v
```

Оба замера без `-Dload.url` пропускаются: это измерения, а не проверки, и в сборке образа им не место.
