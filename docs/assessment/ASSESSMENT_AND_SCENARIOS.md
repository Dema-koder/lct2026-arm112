# Как сейчас оцениваются шаги обучающегося и откуда берутся сценарии

Описание текущего состояния кода (ветка `fix/manual-testing-round-2`, сентябрь 2026). Не проект, а «как есть»: что именно считает сервер, какие веса, какие штрафы, откуда берётся эталон. Роли и виды занятий — в [ROLES.md](../ROLES.md); первоисточники критериев — [materials/q-and-a.md](../materials/q-and-a.md) §6–7, [materials/dds-workflow.md](../materials/dds-workflow.md).

Код: пакет [`service/assessment`](../../src/main/java/ru/lct/arm112/service/assessment/), [`ScenarioService`](../../src/main/java/ru/lct/arm112/service/ScenarioService.java), [`TrainingEngine`](../../src/main/java/ru/lct/arm112/service/TrainingEngine.java), [`CardFillService`](../../src/main/java/ru/lct/arm112/service/CardFillService.java).

---

## 1. Общая схема

```
Библиотека сценариев (ScenarioService)
   TICKET (96 из билетов) · GENERATED (преподаватель) · TRAINEE_MADE (из сохранённых карточек)
          │
          ▼  преподаватель выбирает scenarioIds в занятии
Занятие (LessonService.create/start)
   mode = CARD_FILL | CARD_ACTIONS,  kind = TRAINING | CHECK | EXAM,  intensity
          │
          ▼  на каждого обучающегося — SessionState (TrainingEngine.open)
Поток вводных по интенсивности
   CARD_FILL:    очередь входящих вызовов → черновик карточки → «Сохранить»
   CARD_ACTIONS: карточка в журнале ДДС → принять/отказать → статусы реагирования → завершить
          │
          ▼  submit() обучающимся или forceComplete() преподавателем / автозавершение
Оценка ИИ (CardFillAssessor | CardActionsAssessor) → таблица assessment
          │
          ▼  преподаватель может переопределить критерии (LessonService.assess)
Итог = teacher_total ?? ai_total  →  результаты, рейтинг (RatingService), отчёт занятия
```

«ИИ» в коде — это детерминированные правила, без модели: сравнение с эталоном сценария, Жаккар, Левенштейн, нормативы времени.

---

## 2. Когда происходит оценка

Оценка одна на сессию, считается в `TrainingEngine.complete(state)`, срабатывает:

| Триггер | Кто | Условие |
|---|---|---|
| `POST /training-sessions/{id}/submit` | обучающийся | CARD_ACTIONS: все карточки в терминальном статусе и очередь `pending` пуста; CARD_FILL: `fillFlowFinished` (очередь вызовов пуста, никто не звонит, все черновики `SAVED`). Иначе 422. |
| Автозавершение после `save` последнего черновика | система | только CARD_FILL: `CardFillService.save` → `fillFlowFinished` → `complete` (решение №11 — без лишней кнопки) |
| `POST /teacher/lessons/{id}/complete` | преподаватель | `forceComplete` для каждой активной сессии — оценивается то, что есть |
| Старт нового занятия у того же обучающегося | система | предыдущая активная сессия закрывается через `forceComplete` |

После оценки сессия → `COMPLETED`; если все сессии занятия завершены — занятие тоже `COMPLETED`. Публикуются события `training.session_state_changed` и `assessment.completed`.

Видимость результата обучающемуся (`requireVisible`): для `EXAM` — только после `publish` преподавателем; для `TRAINING`/`CHECK` — сразу.

## 3. Режим CARD_FILL — оператор 112 заполняет карточку

Оценщик: [`CardFillAssessor`](../../src/main/java/ru/lct/arm112/service/assessment/CardFillAssessor.java). Единица оценки — сохранённый черновик `CardDraft`; каждый черновик привязан к сценарию (`scenarioId`), эталон — поля `expectedAddress`, `expectedIncidentTypes`, `expectedServices` сценария.

### 3.1 Критерии и веса

| Критерий | Код | Вес | Что сравнивается |
|---|---|---|---|
| Адрес | `address` | **40** | `draft.address` ↔ `scenario.expectedAddress` через `AddressMatcher` |
| Тип происшествия | `classification` | **20** | Жаккар `draft.incidentTypeIds` ↔ `expectedIncidentTypes` |
| Службы | `services` | **20** | Жаккар кодов `draft.services` ↔ `expectedServices` |
| Время | `timing` | **15** | `savedAt − startedAt` против норматива 3 минуты + штраф за пропущенные вызовы |
| Грамотность | `language` | **5** | `LanguageChecker` по `draft.description` |

Каждый критерий — 0–100 на карточку, усредняется по всем черновикам сессии (`n = max(1, drafts.size())`), итог `total = Σ(критерий × вес) / 100`.

Если у черновика не найден сценарий — все пять критериев по нему получают 100 (защитный случай, на практике не бывает).

### 3.2 Адрес — `AddressMatcher.score`

Стартует со 100, вычитаются штрафы. Перед сравнением обе стороны нормализуются (`TextUtil.normalize`): нижний регистр, `ё→е`, убраны кавычки/знаки препинания и слова-типы (`улица, ул, проспект, пер, шоссе, дом, д, корпус, к, стр, …`).

| Ситуация | Штраф | Issue (severity) |
|---|---|---|
| Улица ожидается, но не указана | −60 | `ADDRESS_STREET_MISSING` (CRITICAL) |
| Улица не совпадает, Левенштейн ≤ 2 и строки не вложены друг в друга — **опечатка** («Дубнинская / Дубининская») | −40 | `ADDRESS_STREET_MISMATCH` (CRITICAL) |
| Одна строка содержит другую (например, введена часть названия) | −5 | — |
| Иначе — другая улица | −60 | `ADDRESS_STREET_WRONG` (CRITICAL) |
| Дом ожидается, но не указан | −20 | `ADDRESS_HOUSE_MISSING` (WARNING) |
| Дом не совпадает | −20 | `ADDRESS_HOUSE_MISMATCH` (WARNING) |
| Населённый пункт указан и не совпадает | −10 | `ADDRESS_LOCALITY_MISMATCH` (WARNING) |
| Корпус / строение / квартира ожидаются и не совпадают | −5 за каждое | `ADDRESS_DETAIL_MISMATCH` (INFO) |

Результат обрезается в [0, 100]. Если у сценария нет `expectedAddress` — 100. Поле `descriptive` (ориентир) в сверке не участвует — только формализованные поля.

### 3.3 Тип происшествия

`jaccard(draft.incidentTypeIds, expectedIncidentTypes) × 100` — доля пересечения к объединению множеств. Частичное совпадение (выбран один из двух ожидаемых, или добавлен лишний) даёт дробный балл.

- Если эталон пуст: балл 100, когда обучающийся тоже ничего не выбрал, иначе 0 (на `save` тип обязателен, так что фактически такой сценарий даст 0).
- `INCIDENT_TYPE_MISMATCH`: CRITICAL при 0 («определён неверно»), WARNING при частичном («не полностью»). В issue подписи типов из справочника.

### 3.4 Службы

Службы в черновике собираются автоматически из матрицы ЕКП (`ReferenceDataService.servicesFor(types)`, файл [`seed/service-matrix.json`](../../src/main/resources/seed/service-matrix.json)) плюс добавленные вручную; автоматические удалить нельзя (`CardFillService.recomputeServices`). Поэтому балл по службам почти целиком зависит от правильности типа.

- Балл: `jaccard(коды служб черновика, expectedServices)`; при пустом эталоне — 100.
- На каждую отсутствующую ожидаемую службу — issue `SERVICE_MISSING`: CRITICAL для 101/102/103/104, WARNING для остальных.

### 3.5 Время

Норматив `NORM = 3 мин` (жёстко в оценщике; таймер на экране берётся из настройки `sla.processing_seconds`, по умолчанию тоже 180).

- `spent = savedAt − startedAt`; `startedAt` — момент принятия вызова (создания черновика).
- `t = 100`, если `spent ≤ 3 мин`; иначе линейно вниз: `100 − 100·(spent − 180)/180`, то есть 0 при 6 минутах и дольше. Issue `PROCESSING_OVERDUE` (WARNING).
- Черновик без `savedAt` (не сохранён к моменту принудительного завершения) — 0 по времени, issue `CARD_NOT_SAVED` (CRITICAL). Остальные критерии по нему считаются по тому, что успели заполнить.

После усреднения к времени применяется штраф за телефонию (см. §5.1): `timing = clamp(timing − 10·missedCalls − 30·lostCalls)`. На каждый пропуск — issue `CALL_MISSED` (WARNING), на каждый потерянный вызов — `CALL_LOST` (CRITICAL).

### 3.6 Грамотность — `LanguageChecker.check(description)`

Не орфографический словарь, а ловля признаков небрежного набора (Q&A §6). Каждая находка — −15, минимум 0; счётчик `syntaxErrors` попадает в отчёт занятия.

| Проверка | Пример находки |
|---|---|
| Латиница и кириллица в одном слове | «Смешаны латиница и кириллица: «Дyбнинская»» |
| Тройная буква подряд | «Тройная буква: «пожааар»» |
| Слово ≥ 5 букв на расстоянии Левенштейна 1 от известного топонима | «Похоже на опечатку в названии: «Дубнинская» вместо «дубининская»» |
| Двойная пунктуация или пробел перед знаком | «Небрежная пунктуация (n)» — одна находка на весь текст |
| Текст > 40 символов целиком в нижнем регистре | «Текст набран без заглавных букв» |

Словарь топонимов (`knownPlaces`) собирается при старте из `expectedAddress.street` и `.locality` всех сценариев (`ScenarioService.learnPlaces`), токены длиной ≥ 5. Пустое описание — 100.

### 3.7 Подсказки по ходу заполнения (`hints`)

Только для занятий вида `TRAINING` и только пока черновик в состоянии `DRAFT` (`CardFillService.withHints`). Не влияют на оценку, возвращаются в `CardDraft.hints`:

- `address.street` — улица не совпадает с эталоном (нормализованное сравнение без вложенности);
- `address.house` — номер дома не совпадает;
- `incidentTypeIds` — ни один выбранный тип не входит в эталон / тип не выбран при уже введённом адресе.

### 3.8 Рекомендации

Добавляются, если критерий < 100: сверять улицу и дом с уточнённым адресом; пользоваться поиском по типу; не удалять автоподобранные службы; укладываться в 3 минуты; проверять набор. Отдельно — «Отвечайте на вызов сразу», если были пропуски.

## 4. Режим CARD_ACTIONS — диспетчер ДДС отрабатывает карточку

Оценщик: [`CardActionsAssessor`](../../src/main/java/ru/lct/arm112/service/assessment/CardActionsAssessor.java). Единица оценки — карточка `CardState` (снимок `MutableCard`) с её таймлайном и исходящими звонками `CallState`.

### 4.1 Критерии и веса

| Критерий | Код | Вес | Что смотрится |
|---|---|---|---|
| Время | `timing` | **30** | флаги `acceptanceOverdue`, `processingOverdue` |
| Действия | `actions` | **40** | терминальный статус ↔ `expectedDecision`, ошибочный отказ, отказ без выезда, обязательный доклад |
| Коммуникация | `communication` | **15** | длина комментариев к статусам |
| Грамотность | `language` | **15** | `LanguageChecker` по всем комментариям карточки |

Усреднение по картам, `total = Σ(критерий × вес)/100`.

### 4.2 Время

Флаги выставляет планировщик `TrainingEngine.detectOverdue` (раз в секунду):

- `acceptanceOverdue` — карточка в `RECEIVED`/`RECEIVED_BY_SERVICE` дольше `sla.acceptance_seconds` (по умолчанию 30 с) от момента появления в журнале (решение №12: открытие карточки не сбрасывает отсчёт). Штраф −40, issue `ACCEPTANCE_OVERDUE`.
- `processingOverdue` — с момента `ACCEPT` прошло больше `sla.processing_seconds` (180 с), а карточка не в терминальном статусе. Штраф −30, issue `PROCESSING_OVERDUE`.

Оба флага липкие: один раз просрочил — штраф остаётся, даже если потом всё сделал.

### 4.3 Действия

Стартует со 100.

| Ситуация | Штраф | Issue |
|---|---|---|
| Карточка не в терминальном статусе (`COMPLETED`, `WORK_REFUSED`, `NOT_ACCEPTED`) | балл 0, остальные проверки не делаются | `CARD_NOT_FINISHED` (CRITICAL) |
| Ожидался `ACCEPT`, итог `NOT_ACCEPTED` — отказ от профильного происшествия | −70 | `REFUSED_PROFILE_INCIDENT` (CRITICAL) |
| Ожидался `DECLINE`, итог `COMPLETED` — принята чужая карточка | −40 | `ACCEPTED_FOREIGN_INCIDENT` (WARNING) |
| Был `DECLINE`, но потом исправлен на «Принята» (при ожидаемом `ACCEPT`) | −10 | `DECLINE_CORRECTED` (INFO) |
| `WORK_REFUSED` без предшествующего `ARRIVE` — отказ от работ без выезда | −20 | `REFUSE_WITHOUT_RESPONSE` (WARNING) |
| Сценарий требует доклад (`outboundCallRequired`), карточка завершена, а звонка в состоянии `ACKNOWLEDGED`/`ENDED` нет | −30 | `CALL_MISSING` (WARNING) |

Откуда берётся `expectedDecision` карточки (`TrainingEngine.cardFrom`): из сценария, если задан; иначе `ACCEPT`, если служба обучающегося (`lesson.serviceCode`, по умолчанию `101`) есть в `expectedServices` сценария, иначе `DECLINE`. Так один и тот же билет для пожарной ДДС — профильный, для полицейской — «не в компетенции».

Примечание: `CALL_MISSING` в оценке практически недостижим — `reaction(COMPLETE)` уже отказывает 422, если обязательный звонок не выполнен. Штраф остаётся на случай принудительного завершения.

### 4.4 Карточка, которую не трогали

Если в таймлайне нет ни одной записи с `actorRole = TRAINEE`, карточка получает 0 по действиям, коммуникации и грамотности (время считается как обычно). Это ситуация «преподаватель завершил занятие, обучающийся до карточки не дошёл».

### 4.5 Коммуникация

Смотрятся записи таймлайна с действиями `DECLINE`, `REFUSE_WORK`, `COMPLETE`, `ACCEPT`. Для всех, кроме `ACCEPT`, комментарий обязателен содержательно: короче 15 символов — −30 и issue `COMMENT_INCOMPLETE` («нет основания или результата»). Формально `DECLINE`/`REFUSE_WORK` без причины и комментария сервер вообще не примет (`requireReason`), а `COMPLETE` требует комментарий по `commentRequiredOnCompletion` (сейчас всегда `true`), поэтому оценщик ловит именно отписки вроде «ок».

### 4.6 Грамотность

Все комментарии карточки склеиваются через «. » и проверяются `LanguageChecker` — те же правила, что в §3.6.

### 4.7 Рекомендации

Открывать карточку сразу (норматив с момента появления в журнале); проверять компетенцию по классификатору перед отказом, ошибочный отказ исправлять статусом «Принята»; комментарий — основание и результат; следить за грамотностью.

## 5. Что ещё влияет на оценку: поток вводных и интенсивность

Занятие задаёт `intensity` (`TrainingEngine.Intensity`), который определяет, как вводные попадают к обучающемуся:

| Интенсивность | Интервал прихода | Фоновых карточек в журнале 112 | Сложность |
|---|---|---|---|
| `SEQUENTIAL` | следующая после закрытия текущей | 0 | 5 |
| `LOW` | 90–180 с | 3 | 3 |
| `MEDIUM` | 45–90 с | 6 | 5 |
| `HIGH` | 15–40 с | 10 | 8 |

Поле `difficulty` у интенсивности пока не используется в подсчёте баллов — только `backgroundCards` и интервалы.

### 5.1 CARD_FILL: очередь вызовов

- При старте первая вводная из `pending` сразу становится вызовом (`arriveNextCall`) и начинает звонить (`presentNextCall`); остальные приходят по таймеру `nextArrivalAt` (в `SEQUENTIAL` — сразу все по мере освобождения).
- Вызов звонит `RING_SECONDS = 30`. Оператор принимает его `POST /card-drafts` — создаётся черновик, `startedAt = now`.
- Не принял за 30 с → `missRingingCall`: `missedCalls++`, заявитель перезванивает через `REDIAL_SECONDS = 20`. Второй пропуск (`MAX_MISSES = 2`) → вводная в `lost`, событие `call.lost`, черновик по ней уже не появится.
- Следующий вызов не предъявляется, пока открыт черновик в состоянии `DRAFT` — оператор занят.
- В оценке: `−10` по времени за каждый пропуск, `−30` за каждый потерянный вызов (§3.5). Потерянная вводная не даёт карточки и не входит в усреднение остальных критериев — то есть потерять вызов «дешевле», чем заполнить его плохо; это стоит иметь в виду.
- Фоновые карточки (`backgroundCards`) — чужие сохранённые карточки других АРМ в журнале, для реалистичности; в оценке не участвуют.

### 5.2 CARD_ACTIONS: журнал ДДС

- Первая карточка доставляется в журнал сразу при старте (`deliverNextCard`); остальные — по таймеру интенсивности, а в `SEQUENTIAL` — когда все текущие карточки в терминальном статусе (`afterCardChange`).
- Норматив 30 с отсчитывается от `receivedAt` — момента появления в журнале, а не открытия.
- При интенсивности выше `SEQUENTIAL` карточки накапливаются, и просрочки по принятию (−40 каждая) — основной механизм «сложности».

## 6. После оценки ИИ: преподаватель, итог, рейтинг

### 6.1 Правка преподавателем — `PUT /teacher/sessions/{id}/assessment`

Тело `TeacherAssessment { total?, comment?, criteria[] }`, `criteria` — список `{code, score?, comment?}` по кодам режима из [`AssessmentWeights`](../../src/main/java/ru/lct/arm112/service/assessment/AssessmentWeights.java).

- Если хотя бы у одного критерия задан `score`: итог пересчитывается сервером `AssessmentWeights.total(ai, criteria)` — по весам режима, балл преподавателя там, где он задан, иначе балл ИИ; критерии без балла ни у кого не входят в расчёт (веса нормируются).
- Если критериев нет, но есть `total` — итог берётся как есть.
- Ни того, ни другого — 422.

### 6.2 Финальная оценка — `AssessmentRepository.finalOf`

`totalScore = teacherTotal ?? aiTotal`; по каждому критерию — балл преподавателя, если задан, иначе ИИ. `source = TEACHER | AI`. Issues и recommendations всегда от ИИ, `aiTotalScore` сохраняется отдельно, чтобы правка была видна.

### 6.3 Рейтинг — `RatingService`

`coalesce(teacher_total, ai_total)` по всем завершённым сессиям обучающегося; рейтинг — среднее, место в группе — по числу участников с бо́льшим средним. Вид занятия и режим не различаются — тренировка и зачёт весят одинаково.

### 6.4 Отчёт занятия

`GET /teacher/lessons/{id}/report(.csv)`: по каждой сессии — `timingScore`, `syntaxErrors`, рейтинг, `aiTotal`, `teacherTotal`, `finalTotal`, состояние. Сортировка по итогу.

## 7. Откуда берутся сценарии

Сценарий (`ApiModels.Scenario`) — это вводная + эталон:

| Поле | Роль |
|---|---|
| `callerText` | что говорит заявитель (показывается обучающемуся) |
| `caller` | ФИО, телефон |
| `rawAddress` | адрес словами заявителя (показывается) |
| `expectedAddress` | формализованный эталон для `AddressMatcher` (не показывается) |
| `expectedIncidentTypes`, `expectedServices` | эталон типа и служб |
| `expectedDecision`, `expectedDecisionReason`, `outboundCallRequired` | эталон для CARD_ACTIONS |
| `source` | `TICKET` / `GENERATED` / `TRAINEE_MADE` |
| `category`, `difficulty` | фильтры для библиотеки и генерации (в оценке не участвуют) |
| `referenceConfirmed` | преподаватель подтвердил эталон |

### 7.1 `TICKET` — сид из билетов

[`seed/scenarios.json`](../../src/main/resources/seed/scenarios.json): 96 сценариев, размеченных вручную из билетов заказчика ([materials/tickets.md](../materials/tickets.md)). Категории: OTHER 32, FIRE 25, MEDICAL 25, POLICE 7, RESCUE 4, GAS 2, UTILITY 1. Загружаются один раз при пустой таблице (`ScenarioService.seed`); при последующих стартах только достраиваются названия (`backfillTitles`) и обновляется словарь топонимов для `LanguageChecker`.

Название сценария (`autoTitle`): подпись первого типа происшествия + улица (или населённый пункт / ориентир); без типа — первые 60 символов вводной.

### 7.2 `GENERATED` — шаблонная генерация преподавателем

`POST /teacher/scenarios/generate { category, count ≤ 20, difficulty }` → `ScenarioService.generate`:

1. Берётся пул `TICKET`-сценариев категории (нужно ≥ 2, иначе 422).
2. `count` раз: случайно выбирается сценарий-**источник ситуации** и случайно — сценарий-**источник адреса** (могут совпасть).
3. Новый сценарий = `callerText`, `caller`, `expectedIncidentTypes`, `expectedServices` от ситуации + `rawAddress`, `expectedAddress`, `addressClarified` от адреса. `expectedDecision = ACCEPT`, `outboundCallRequired = true`, `referenceConfirmed = false`, название «Сгенерировано: …».

Никакой языковой модели нет — это перекомбинирование билетов; комбинация может быть неестественной (текст про подъезд, адрес — железнодорожный переезд). Поэтому сгенерированные сценарии предполагают проверку: `POST /teacher/scenarios/{id}/confirm-reference`. Подтверждение сейчас ни на что в оценке не влияет — только на приоритет отбора фоновых карточек и на флаг в списке.

Ручное создание/правка: `POST/PUT /teacher/scenarios` (`ScenarioUpsert`). Если `expectedServices` не переданы, они вычисляются по ЕКП из типов (`references.servicesFor`); `addressClarified = expectedAddress != null`. Созданный вручную получает `source = GENERATED`.

### 7.3 `TRAINEE_MADE` — карточки, сохранённые обучающимися

При каждом `POST /card-drafts/{id}/save` (`CardFillService.save`) создаётся сценарий `trainee-…` (`ScenarioService.saveTraineeMade`):

- `callerText` — описание из карточки (если пустое — вводная базового сценария);
- `rawAddress` — адрес, введённый обучающимся, в текстовом виде (`describe`);
- **эталон берётся от базового сценария** (`expectedAddress`, типы, службы), а не из карточки: типы/службы обучающегося попадают в эталон только если у базового они пустые;
- `expectedDecision = ACCEPT`, `outboundCallRequired = true`.

Задумка по ТЗ (сценарий 3): карточка оператора 112 становится вводной для диспетчера ДДС в режиме CARD_ACTIONS. На практике при `cardSource = TRAINEE_MADE` диспетчер увидит текст и адрес в том виде, как их ввёл оператор (включая ошибки), а оцениваться будет по эталону билета. Сценарии `TRAINEE_MADE` создаются при каждом сохранении, без дедупликации.

### 7.4 Как сценарии попадают в занятие

- Преподаватель передаёт явный список `scenarioIds` в `POST /teacher/lessons`; `cardSource` (`GENERATED` / `TRAINEE_MADE` / `MIXED`) сейчас только валидируется и сохраняется — отбор по нему в `LessonService.create` не выполняется. `ScenarioService.pick(source, count, random)` реализует случайный отбор по источнику (`GENERATED` → TICKET+GENERATED, `TRAINEE_MADE`, `MIXED` → все), но нигде не вызывается — мёртвый код.
- При старте занятия список `scenarioIds` целиком кладётся в `pending` каждой сессии в заданном порядке — у всех участников одна и та же последовательность вводных.
- Фоновые карточки журнала 112 (`backgroundCards`) выбираются случайно из библиотеки, исключая сценарии занятия и `TRAINEE_MADE`; подтверждённые эталоны — первыми.

## 8. Сводка ограничений текущей реализации

Не баги, а место, где реализация проще, чем формулировки в ТЗ; полезно знать, когда читаешь баллы.

1. Оценка чисто правиловая; ни один критерий не учитывает `difficulty` сценария или интенсивность — «сложность» проявляется только через просрочки и пропуски.
2. Потерянный вызов (CARD_FILL) штрафует только время (−30 из 15 % веса ≈ −4,5 итоговых балла) и исключает вводную из усреднения остальных критериев.
3. `expectedAddress.descriptive` и опросные ответы (`surveyAnswers`), флаги карточки (`flags`), телефоны и ФИО заявителя не оцениваются.
4. Генерация сценариев — перекомбинирование билетов внутри категории; `referenceConfirmed` в оценке не участвует.
5. `cardSource` занятия не влияет на подбор сценариев — работает только явный список `scenarioIds`.
6. Эталон `TRAINEE_MADE` наследуется от базового билета, а не от того, что ввёл обучающийся.
7. Рейтинг усредняет все завершённые сессии без учёта вида занятия.
