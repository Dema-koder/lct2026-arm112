# Замысел: эмбеддинги для подбора типа происшествия

Отложенная идея, не реализована. Развивает [ASSESSMENT_ML_ROADMAP.md §2.2](ASSESSMENT_ML_ROADMAP.md) с учётом того, что выяснилось при реализации `D2`.

## Откуда взялась

`D2` сделан на взвешенном совпадении признаков (синонимы из справочника + подписи типов). Замер на 76 размеченных билетах: **top-1 65.8 %, top-3 94.7 %, macro-F1 0.548**. *Поправка 28.09: та разметка была сделана тем же поиском по ключевым словам (`tools/build_seed.py`), то есть классификатор сверялся сам с собой. На ручной разметке всех 96 билетов — top-1 36.5 %, top-3 56.3 %, macro-F1 0.35 (`IncidentTypeClassifierTest`).* Отсюда решение показывать список из трёх кандидатов, а не один ответ.

Разбор ошибок показал, что примерно половина из них одного рода: **нет пересечения по словам**. «Плохо с сердцем, задыхается» не находит тип «Внезапное заболевание», потому что ни одно слово не совпадает с синонимами. Совпадение признаков такие пары принципиально не ловит — а эмбеддинги ловят.

## Что именно предлагается

**Zero-shot на прототипах классов.** Прототип типа = эмбеддинг его подписи и синонимов. Классификация = косинусная близость эмбеддинга текста заявителя к прототипам.

Ключевое свойство: **обучающая выборка не нужна вообще**. Это важно, потому что данных для обучения нет и в ближайшее время не будет (см. ниже).

Комбинировать с нынешним методом имеет смысл сложением рангов: там, где совпали слова, ключевой метод точнее и объяснимее; там, где парафраз, вытягивают эмбеддинги.

## Что для этого нужно

| Что | Объём | Комментарий |
|---|---|---|
| `rubert-tiny2` в формате ONNX | ≈ 120 МБ | Тот же вопрос доставки весов, что и с LLM, но на два порядка меньше |
| ONNX Runtime для JVM | ≈ 15 МБ | Инференс внутри приложения, без Python-сайдкара |
| Токенизатор | — | Идёт с моделью |

Данных не нужно **ничего** — в этом и смысл варианта.

## Как проверять

Честное сравнение на той же выборке и той же метрикой, что уже снята для `D2`:

| Метрика | Сейчас (признаки) | Порог для замены |
|---|---|---|
| top-1 | 65.8 % | > 70 % |
| top-3 | **96.1 %** | > 96 % |
| macro-F1 | 0.590 | > 0.62 |
| Задержка | < 1 мс | ≤ 50 мс |
| Память | ~0 | ≤ 600 МБ |

Отдельно — **доля ошибок без пересечения по словам**: именно её эмбеддинги должны сократить. Если общая точность выросла, а эта доля нет, прирост случайный.

Проверка ставится в `IncidentTypeClassifierTest` рядом с нынешней, чтобы цифры считались одним кодом на одних данных.

## Сколько данных нужно другим вариантам

Посчитано по фактической библиотеке: 66 типов, 76 размеченных вводных, медиана 2 примера на покрытый тип.

| Вариант | Примеров на класс | Всего | Реалистичность |
|---|---|---|---|
| Zero-shot на прототипах | **0** | 0 | Доступно сразу |
| kNN поверх замороженных эмбеддингов | 5–10 | 330–660 | Несколько проведённых занятий |
| Линейный слой поверх эмбеддингов | 20 | 1320 | Полугодие эксплуатации |
| Дообучение трансформера | 50–100 | 3300–6600 | В обозримом будущем нереалистично |

Данные копятся сами: `IncidentTypeClassifier.learn` подключён к подтверждению эталона преподавателем, каждое подтверждение добавляет разметку.

## Требования помимо количества

- **Сбалансированность.** Сейчас в категории OTHER 37 типов, в GAS — один. Без взвешивания классов модель уедет в частые.
- **Отложенная выборка по билетам, а не по вводным.** Три вводные одного билета похожи; случайное разбиение завысит цифры.
- ~~31 тип не покрыт ничем~~ — **утверждение неверно, исправлено в [SYNONYMS_AUDIT.md](SYNONYMS_AUDIT.md)**. Эти 31 запись — верхний уровень списка «что случилось?», а не цели классификации; все 35 типов ЕКП синонимами покрыты.
