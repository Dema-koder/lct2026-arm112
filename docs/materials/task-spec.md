# Техническое задание — выжимка

Источник: `materials/9. Деп Обороны и ЧС.pdf` (20 страниц).
Постановщик — Департамент ГО, ЧС и пожарной безопасности города Москвы. Направление «Город», задача №9 ЛЦТ 2026.

Полное название: **«Учебное программное обеспечение для подготовки оператора ДДС города Москвы с использованием искусственного интеллекта»**.

Ниже — только то, что влияет на реализацию. Разделы про юридические основания, определения терминов и общие формулировки опущены; при необходимости смотри оригинал.

## Что строим

Тренажёр для подготовки операторов ДДС, работающих с системой-112 Москвы. Не обрабатывает реальные вызовы, только имитирует. Локальный контур без выхода в интернет.

Четыре обязательных компонента по ТЗ:

- система эмуляции вызовов (VoIP / IP-телефония);
- модуль управления обучением с уровнями сложности;
- компонент оценки действий обучающегося (ИИ / ML);
- интерфейс преподавателя для контроля процесса.

## Роли (три, по ТЗ и подтверждено на Q&A)

**Администратор** — запуск/остановка сервисов, мониторинг состояния, обновление ПО, резервное копирование; создание учётных записей, назначение ролей, блокировка; настройка телефонии, БД, политик доступа, журналирования; просмотр системных журналов и отчётов об ошибках.

**Преподаватель** — выбор категорий событий и настройка генерации; формирование и подтверждение «эталона» (эталонных ответов, с которыми сравниваются действия обучающегося); предпросмотр сгенерированных вопросов с подсветкой правильных вариантов; коррекция через контекстное поле комментария; загрузка материалов в базу; раздача заданий адресно по рабочим местам; старт и завершение занятия; формирование отчёта.

**Обучающийся** — доступ к назначенным сценариям и методическим материалам; выполнение практических заданий; приём входящих сообщений/вызовов в режиме обучения; ввод текстовых ответов в карточку; просмотр своих результатов, статистики, ошибок и рекомендаций; таймер выполнения в интерфейсе.

Обучающемуся **запрещено**: административные и преподавательские функции, изменение учебных материалов, удаление результатов, изменение настроек, доступ к результатам других обучающихся.

## Сценарии из ТЗ

**Настройка учебной среды** (преподаватель): вход → выбор категории событий и настройка генерации → автоформирование эталона → подтверждение эталона преподавателем → настройка ролевой модели (чтобы в ленту обучающегося попадали только профильные события) → предпросмотр вопросов/ответов с подсветкой правильных → коррекция комментарием → загрузка материалов → проверка грамматики.

**Практическое занятие, карточки**: вход → выбор категорий → старт → система имитирует звонок → обучающийся заполняет карточку → преподаватель завершает занятие → отчёт (действия, ошибки, время заполнения, отличие от норматива, грамматика).

**Практическое занятие, действия с карточками**: то же, но преподаватель дополнительно выбирает источник карточек — сгенерированные системой, сформированные обучающимися или смешанно. Система выдаёт случайную карточку, обучающийся производит действия, включая ввод текста («Сообщение принято, дежурная бригада направлена на место»), после завершения получает следующую карточку.

> Второй сценарий — это то, что реализовано в текущем прототипе (`CARD_ACTIONS`).

## Нормативы времени

- **30 секунд** — реакция на сообщение в строке состояния (открыть, подтвердить приём). Это норматив из ПП РФ №1931, он же зафиксирован в памятке ДДС.
- **3 минуты** — отработка карточки. Этот норматив установлен заказчиком прямо на сессии Q&A, в ТЗ его нет.

## Производительность (в локальной сети)

| Параметр | Требование |
|---|---|
| Время отклика интерфейса | ≤ 2 с при нагрузке до 100 пользователей |
| Одновременные сессии | ≥ 20 (вызовов/карточек) |
| Задержка VoIP | ≤ 150 мс |
| Сбой сети | до 30 с с автовосстановлением сессий без потери данных |
| Запись в БД | ≥ 100 операций/с |
| Формирование отчётов | ≤ 30 с |

На Q&A уточнили: жёстко нагрузку проверять не будут, но отваливаться на десяти одновременных пользователях нельзя — в реальном классе 20-30 человек.

## Нефункциональные требования

- Резервное копирование не реже 1 раза в сутки.
- Журналирование всех значимых событий, аудит действий пользователей.
- Многоуровневая аутентификация (в рамках локальной сети), TLS/SSL внутри контура, RBAC.
- Хранение журналов безопасности не менее 6 месяцев.
- ОС: Windows 10/11, Linux Ubuntu 20.04+. Браузеры: Chrome, Firefox, Яндекс.Браузер.
- **СУБД: PostgreSQL 12+.**
- VoIP через локальный SIP-сервер.
- Документированные процедуры установки, настройки и восстановления.

## Форматы данных

JSON — обмен между компонентами, профили пользователей, сценарии обучения, логи.
XML — конфигурации, структурирование методических материалов.
CSV — выгрузка отчётов и статистики.
SQL — основная БД.
MP3/WAV — аудиозаписи учебных вызовов.
PDF — документация, сертификаты. DOCX — методические материалы.

## Границы решения

Сервис **не должен**: обрабатывать реальные экстренные вызовы; содержать функционал основной системы-112 (только имитация); работать с конфиденциальной информацией вне учебного процесса; выполнять функции реального диспетчерского центра.

## Опциональные модули

Расширенная аналитика (графики, тепловые карты ошибок); экспорт отчётности в Excel/PDF; пакетное обновление учебных материалов; адаптивный веб-интерфейс для мобильных в рамках локальной сети; внутренний API для расширения.

## Требования к сдаче

1. Ссылка на репозиторий с кодом.
2. Ссылка на презентацию (pptx или pdf).
3. Ссылка на прототип для проверки.
4. Ссылка на сопроводительную документацию (.docx/.pdf).

Сопроводительная документация обязана описывать: используемые методы обработки данных; условия и ограничения внутри решения; подробные инструкции по компиляции, сборке и установке; функциональную и компонентную архитектуру. Код — открытый, без обфускации, с перечнем всех библиотек.

## Критерии экспертизы

Предварительная и финальная экспертиза оценивают одно и то же по четырём осям:

1. **Подход**: идея, оригинальность, способ реализации, технологии.
2. **Техническая проработка**: качество кода, возможность интеграции в другие системы, скорость работы.
3. **Эффективность**: проверка расчётов и прогнозирования, достоверность; на финале — сравнение прогнозных значений с реальными, проверка рекомендаций, настраиваемые параметры, объективность диаграмм.
4. **Соответствие задаче**: полнота документации, UX/UI, логически связанные блоки рядом.

Плюс выступление на питч-сессии.

> Важная поправка с Q&A: «ни оригинальность, ни техническая проработанность сами по себе не решают — главное, насколько решение похоже на то видение, которое озвучил заказчик». См. [q-and-a.md](q-and-a.md), раздел 17.

## Требования к UX/UI

Интуитивные сценарии; каждый элемент решает задачу и присутствует, только если нужен; десктоп и мобильная версия (планшеты и горизонтальные устройства могут использовать десктопную).

При этом на Q&A заказчик просил **держаться реального интерфейса АРМ-112, включая цветовые решения, и минимизировать самодеятельность** — см. [dds-workflow.md](dds-workflow.md) и [screenshots/](screenshots/).
