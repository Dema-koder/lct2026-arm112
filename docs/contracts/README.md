# Контракт фронтенда обучающегося и бэкенда тренажёра АРМ-112 ДДС

Версия: `0.2.0-draft`  
Область: интерфейс обучающегося — сотрудника ДДС  
Машиночитаемая часть: [`openapi.yaml`](./openapi.yaml)  
Эталон для моков: [`examples/dds-card.json`](./examples/dds-card.json)

## 1. Зафиксированный сценарий MVP

Обучающийся не играет роль оператора 112 и не заполняет первичную карточку со слов заявителя. Преподаватель и генератор сценариев формируют готовую карточку, после чего она появляется в очереди АРМ ДДС.

Цепочка работы:

1. Обучающийся входит в систему и видит назначенное рабочее место и занятие.
2. В очередь может поступить одна или несколько готовых карточек.
3. Для каждой карточки обучающийся за 30 секунд выбирает `Принято` или `Не принято`.
4. После принятия за 3 минуты выполняет необходимые действия: начинает реагирование, совершает исходящий учебный звонок должностному лицу, добавляет комментарий и завершает работы либо фиксирует отказ.
5. Бэкенд сохраняет хронологию, просрочки и результат оценки.

Режим создания карточки оператором 112 (`CALL_CARD`) не входит в API версии 0.2. Его можно добавить отдельным модулем, не меняя DTO текущего режима.

## 2. Граница ответственности

### Фронтенд обучающегося

- максимально близко воспроизводит экран АРМ ДДС по предоставленным скриншотам: таблицу карточек, карточку, кнопки состояний, комментарии и визуальные предупреждения;
- использует только серверные идентификаторы и разрешённые команды `allowedActions`;
- показывает таймеры относительно `serverTime`, но не принимает бизнес-решения по локальным часам;
- поддерживает несколько одновременно активных карточек и не теряет выбранную строку при обновлении очереди;
- воспроизводит аудио программного симулятора звонка;
- восстанавливает WebSocket и получает пропущенные события;
- работает с mock-сервером, построенным из OpenAPI.

Фронтенд не создаёт первичную карточку, не классифицирует происшествие, не вычисляет список служб, сроки, итоговый балл и разрешённые переходы.

### Бэкенд

- аутентифицирует обучающегося и привязывает его к рабочему месту;
- принимает назначение занятия от преподавательского контура и выдаёт активную сессию;
- доставляет готовые карточки в очередь;
- является источником истины для времени и state machine;
- обеспечивает идемпотентность команд и аудит;
- управляет симуляцией исходящего звонка и медиаматериалами;
- оценивает сроки, последовательность действий, выбранного адресата, комментарии и критические ошибки;
- публикует события реального времени.

Контракт преподавателя и администратора в этот файл не входит. Их действия отражаются для обучающегося через состояние сессии и WebSocket.

## 3. Транспорт и общие правила

- REST JSON по HTTPS: `/api/v1`.
- WebSocket: `/ws/v1`.
- Авторизация: Bearer JWT; refresh token — `HttpOnly` cookie.
- Даты: ISO 8601 UTC.
- Идентификаторы: UUID v4.
- Локаль: `ru-RU`.
- `X-Contract-Version: 0.2` обязателен для клиента.
- `X-Request-Id` отправляет клиент, сервер возвращает его в ответе.
- `Idempotency-Key` обязателен для всех команд изменения состояния.
- Повтор команды с тем же ключом и телом возвращает первоначальный результат; с другим телом — `409 IDEMPOTENCY_CONFLICT`.
- Серверное время передаётся в `TraineeContext`, `TrainingSession`, `CardPage` и событиях.
- Неизвестное необязательное поле клиент игнорирует. Неизвестный enum отображает как `UNKNOWN` и не падает.

## 4. Экраны и API

| Экран/область | REST | События |
|---|---|---|
| Вход | `POST /auth/login`, `GET /auth/me` | — |
| Рабочее место | `GET /trainee/context` | `training.session_state_changed` |
| Очередь карточек | `GET /cards` | `card.received`, `card.updated`, `card.acceptance_overdue` |
| Просмотр карточки | `GET /cards/{cardId}` | `card.updated` |
| Принятие карточки | `POST /cards/{cardId}/acceptance` | `card.updated` |
| Реагирование | `POST /cards/{cardId}/reaction-events` | `card.updated` |
| Исходящий звонок | `POST /cards/{cardId}/outbound-calls`, `GET /outbound-calls/{callId}`, `POST .../end` | `outbound_call.updated` |
| Завершение занятия | `POST /training-sessions/{sessionId}/submit`, `GET /assessments/{assessmentId}` | `assessment.completed` |

## 5. State machine карточки

Состояния карточки:

```text
RECEIVED ── ACCEPT ──> ACCEPTED ── START_RESPONSE ──> RESPONSE_STARTED ── COMPLETE ──> COMPLETED
    │                       │                              │
    └── DECLINE ──> NOT_ACCEPTED                          └── REFUSE_WORK ──> WORK_REFUSED
```

- `DECLINE` требует `reasonCode` или непустой `comment`.
- `REFUSE_WORK` требует `reasonCode` или непустой `comment`.
- `COMPLETE` допускается только после обязательных действий сценария, включая звонок, если он задан.
- Терминальные состояния: `NOT_ACCEPTED`, `COMPLETED`, `WORK_REFUSED`.
- Бэкенд возвращает `allowedActions`; фронтенд строит кнопки только по этому массиву.
- Любой переход повторно проверяется сервером.

Сроки находятся в `card.sla`:

- `acceptanceDeadlineAt` — обычно `receivedAt + 30 секунд`;
- `processingDeadlineAt` — появляется после принятия, обычно `acceptedAt + 3 минуты`;
- `acceptanceOverdue` и `processingOverdue` фиксируются сервером и не отменяются последующим действием.

Просрочка сама по себе не закрывает карточку: обучающийся продолжает работу, а нарушение учитывается при оценке.

## 6. Готовая карточка ДДС

`IncidentCard` содержит полученные от 112 данные и является для обучающегося read-only, кроме команд реагирования:

- номер и время карточки;
- источник и направившее подразделение;
- заявитель и телефон;
- адрес и координаты;
- описание и тип происшествия;
- признаки и назначенные службы;
- текущий статус и разрешённые действия;
- хронологию действий;
- исходящие учебные звонки;
- требования конкретного сценария.

Редактирование исходных данных карточки и endpoint `PATCH /cards/{id}` удалены из MVP. Комментарий передаётся только вместе с конкретной командой, поэтому его невозможно сохранить без аудита.

## 7. Исходящий учебный звонок

Звонок полностью программный и не требует SIP, аппаратного телефона или внешней сети.

1. Фронтенд получает доступных адресатов в `card.callTargets`.
2. Отправляет короткий номер в `POST /cards/{cardId}/outbound-calls`.
3. Бэкенд возвращает звонок в `DIALING` и затем публикует переходы `RINGING`, `CONNECTED`, `ACKNOWLEDGED`, `ENDED`.
4. В `media` могут быть URL гудка, фразы ответа и подтверждения. URL короткоживущие и доступны только авторизованному пользователю.
5. Обучающийся завершает соединение командой `POST /outbound-calls/{callId}/end`; учебный движок также может закончить его автоматически.

Состояния звонка: `DIALING`, `RINGING`, `CONNECTED`, `ACKNOWLEDGED`, `ENDED`, `NO_ANSWER`, `FAILED`, `CANCELLED`.

## 8. Real-time

Одноразовый ticket для WebSocket выдаёт `POST /auth/ws-ticket`, срок жизни — не более 30 секунд. Access token в URL не передаётся.

Обязательные типы событий:

- `card.received`;
- `card.updated`;
- `card.acceptance_overdue`;
- `card.processing_overdue`;
- `outbound_call.updated`;
- `training.session_state_changed`;
- `assessment.completed`;
- `system.connection_warning`.

`sequence` монотонно растёт в пределах сессии. После переподключения фронтенд вызывает `GET /training-sessions/{sessionId}/events?afterSequence=N`. Любое событие считается уведомлением: после него клиент запрашивает актуальный REST-ресурс и не пытается самостоятельно сливать частичные модели.

Если соединение отсутствует до 30 секунд, фронтенд показывает предупреждение, сохраняет открытый экран и переподключается. Неотправленные команды повторяются только с исходным `Idempotency-Key`.

## 9. Ошибки

```json
{
  "error": {
    "code": "INVALID_STATE_TRANSITION",
    "message": "Действие недоступно в текущем состоянии карточки",
    "requestId": "a12b8e62-b70e-4f5a-b98e-5d76f7c10f87",
    "fieldErrors": [],
    "details": {"currentState": "COMPLETED"}
  }
}
```

Минимальный набор кодов: `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `INVALID_STATE_TRANSITION`, `IDEMPOTENCY_CONFLICT`, `SESSION_NOT_ACTIVE`, `CARD_NOT_ASSIGNED`, `CALL_ALREADY_ACTIVE`, `CALL_TARGET_NOT_ALLOWED`, `MEDIA_UNAVAILABLE`, `SESSION_EXPIRED`, `CONTRACT_VERSION_UNSUPPORTED`, `RATE_LIMITED`, `INTERNAL_ERROR`.

## 10. Mock-first и приёмка

`openapi.yaml` — единственный источник истины для REST DTO. Фронтенд генерирует из него типы и mock-server; бэкенд проверяет ответы contract-тестами.

Обязательные mock-сценарии:

- одна новая карточка, принятая вовремя;
- две карточки, поступившие во время обработки первой;
- просрочка 30 секунд без автоматического закрытия;
- отказ без причины — `422`;
- полный цикл `ACCEPT → START_RESPONSE → звонок → COMPLETE`;
- звонок на неверный или недоступный короткий номер;
- отказ от выполнения работ с комментарием;
- потеря WebSocket и восстановление событий;
- попытка повторной команды с тем же idempotency key;
- завершённая оценка с ошибкой адресата, времени и комментария.

Фронтенд готов к интеграции, если:

- собирается по типам версии 0.2 и проходит mock-сценарии;
- не содержит локальной state machine;
- правильно показывает параллельные карточки и оба таймера;
- обрабатывает `400`, `401`, `403`, `404`, `409`, `422`, `426`, `429`, `500`;
- восстанавливает WebSocket и не дублирует команды;
- визуальные regression-тесты покрывают очередь, карточку, модальное окно выбора действия и симулятор звонка.

Бэкенд готов к интеграции, если:

- ответы проходят OpenAPI validation;
- серверное время является источником истины;
- команды идемпотентны, переходы проверяются сервером;
- каждая команда и просрочка попадает в аудит;
- поддерживаются не менее 20 параллельных карточек/звонков;
- примеры из контракта доступны в seed-окружении.

Совместная приёмка: сценарий `вход → поступление готовой карточки → принятие → начало реагирования → исходящий звонок → завершение → оценка` проходит без изменения DTO и без перекомпиляции фронтенда при переключении с mock URL на тестовый бэкенд.
