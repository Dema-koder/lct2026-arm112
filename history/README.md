# История версий

Здесь лежат записи о том, что было сделано перед каждым пушом в ветку. Одна запись — один пуш.

Назначение: через неделю никто не вспомнит, почему в контракте появилось поле `senderLabel` или откуда взялся статус «Получена службой». Запись отвечает на это за минуту, без раскопок в диффах. Плюс из этих записей собирается сопроводительная документация, которую требует ТЗ ([task-spec.md](../docs/materials/task-spec.md), «Требования к сдаче»).

## Как называть файл

```
ГГГГ-ММ-ДД-краткая-тема.md
```

Например: `2026-09-19-status-machine.md`. Если в один день два пуша — добавить номер: `2026-09-19-2-hotfix-css.md`.

## Что писать

Шаблон — [_template.md](_template.md). Разделы:

| Раздел | Зачем |
|---|---|
| Шапка | дата, ветка, коммит, одна фраза о сути |
| Что сделано | по областям: фронтенд / бэкенд / контракт / документация |
| Почему так | решения, которые неочевидны из кода, и на что опирались |
| Проверено | чем именно подтверждено, что работает |
| Не сделано | сознательно отложенное, чтобы не искать заново |
| Требует внимания | грабли для следующего, кто тронет этот код |

## Правила

**Ссылаться на первоисточник.** Если поведение взято из памятки ДДС или ответов заказчика — дать ссылку на файл в [docs/materials/](../docs/materials/). Решение «статусы только последовательно» стоит ровно столько, сколько стоит строчка памятки, на которую оно опирается.

**Писать про отменённые решения.** Если что-то сделали, а потом откатили — это тоже запись. Она дороже, чем описание того, что осталось: следующий человек не полезет туда второй раз.

**Не пересказывать дифф.** «Изменён page.tsx» бесполезно. «Кнопка завершения занятия перенесена в журнал, потому что после отказа от карточки занятие нельзя было сдать» — полезно.

**Отмечать правки контракта отдельно.** В `openapi.yaml` стоит `additionalProperties: false`, поэтому любое новое поле в ответе — ломающее изменение для строгих клиентов. Такие правки должны быть видны в записи сразу.
