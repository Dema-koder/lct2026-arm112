# 2026-09-19 — сохранение в PostgreSQL и Docker Compose

**Ветка:** `main`  
**Коммит:** `—` (заполнить после коммита)  
**Суть:** состояние учебного сценария и realtime-журнал переживают перезапуск backend, а весь стенд запускается одной командой Docker Compose.

## Что сделано

### Фронтенд

- Добавлен production Dockerfile с отдельными этапами сборки и запуска, непривилегированным пользователем и health check.
- Публичные адреса REST и WebSocket передаются в сборку через `NEXT_PUBLIC_*`.

### Бэкенд

- Подключены Spring JDBC, PostgreSQL driver и Flyway для Spring Boot 4.
- Добавлена первая миграция с таблицами snapshot состояния и durable realtime-событий.
- Сессия, карточки, timeline, звонки и итоговая оценка загружаются из БД при старте и сохраняются после каждой команды или планового перехода.
- Номера realtime-событий продолжаются от сохранённого максимума; REST replay читает события из PostgreSQL.
- Тестовый профиль использует H2 в режиме совместимости с PostgreSQL и применяет те же Flyway-миграции.

### Контракт

- Без изменений: URL, DTO, статусы и правила взаимодействия frontend/backend сохранены.

### Документация

- Добавлена инструкция по Compose, локальной разработке с контейнерной БД, просмотру данных, сбросу volume и диагностике.
- Основной README и frontend README обновлены под постоянное хранение.

## Почему так

Для MVP состояние единственного учебного контура хранится атомарным JSON-снимком, а realtime-журнал — отдельными строками. Это минимизирует риск изменения уже согласованной state machine и DTO, при этом обеспечивает требуемое восстановление состояния и событий. При появлении нескольких параллельных занятий snapshot можно постепенно заменить нормализованными таблицами без изменения публичного контракта.

PostgreSQL наружу публикуется на `55432`, чтобы не конфликтовать с типичной локальной установкой на `5432`. Внутри Compose backend обращается к сервису `postgres:5432`.

## Проверено

- `mvn clean verify` — Flyway поднимает тестовую схему, полный учебный сценарий завершается, snapshot и оценка читаются из БД.
- `npm run lint` и `npm test` — frontend lint, production-сборка и интеграционные проверки.
- `docker compose config` — итоговая конфигурация валидна.
- Полный стенд собран и запущен в Docker на альтернативных портах; frontend, backend и PostgreSQL прошли health checks.
- После открытия и принятия карточки контейнер backend перезапущен: статус, timeline и два realtime-события восстановились из PostgreSQL.

## Не сделано

- Snapshot ещё не разложен по нормализованным предметным таблицам: для одного демонстрационного занятия это добавило бы миграционный и ORM-код без пользы для текущего API.
- Cache ключей идемпотентности не сохраняется между процессами; само состояние после успешной команды сохраняется.
- Snapshot и realtime-событие пока записываются раздельно, без transactional outbox.
- Горизонтальное масштабирование backend этой версией не поддерживается.

## Требует внимания

- Уже применённый файл `V1__training_state.sql` нельзя редактировать; изменения схемы нужно оформлять следующей Flyway-миграцией.
- `docker compose down` сохраняет данные, а `docker compose down -v` безвозвратно удаляет volume PostgreSQL.
- После изменения `NEXT_PUBLIC_*` frontend нужно пересобрать, потому что значения встраиваются в bundle.
