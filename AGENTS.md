# Правила работы с репозиторием для ИИ-агентов

Для Claude Code, Codex и любого другого агента. Читается в начале каждой сессии — поэтому коротко. Подробности не дублируются: история — [history/README.md](history/README.md), незакрытые вопросы — [improvements/open-issues.md](improvements/open-issues.md), материалы заказчика — [docs/materials/README.md](docs/materials/README.md).

## 1. Начало сессии — обзор за 5 команд

Выполнить ровно это, ничего больше не читая:

```bash
git pull --ff-only                     # если не fast-forward — сказать пользователю, не мержить молча
git log --oneline -15
git diff --stat HEAD@{1} HEAD          # что пришло с прошлого раза
ls -t history | head -3                # новые записи истории
git status --short
```

Затем прочитать **только** новые файлы из `history/` (те, которых не было) и, если в них есть раздел «Не сделано», сверить с [improvements/open-issues.md](improvements/open-issues.md).

Выдать пользователю 5–10 строк:
- что появилось в ветке (по коммитам, не по диффу);
- какие пункты из «Не сделано» новых записей истории ещё не закрыты;
- что из `materials/` не разобрано в `docs/materials/` (сверить список файлов, не открывая их);
- незакоммиченные изменения в рабочем дереве, если есть.

Не открывать `materials/*.docx|pdf`, `improvements/ChatExport_*`, `docs/contracts/openapi.yaml` целиком и не запускать сборку ради обзора — это дорого и в 90 % случаев не нужно.

## 2. Конец работы — запись в history/

Перед пушем создать `history/ГГГГ-ММ-ДД-N-тема.md` по шаблону [history/_template.md](history/_template.md): что сделано (фронтенд / бэкенд / контракт / документация), почему так, чем проверено, что не сделано, что требует внимания. Правила — в [history/README.md](history/README.md). Одна запись — один пуш.

Если правился `docs/contracts/openapi.yaml` — поднять версию и отметить это в записи отдельной строкой: там `additionalProperties: false`, любое новое поле ломает строгих клиентов.

## 3. Коммит и пуш

1. Ветка: работать в отдельной (`feat/…`, `fix/…`, `docs/…`), **не в `main`**.
2. Коммит: заголовок по-русски одной строкой, тело — списком что и зачем. **Без `Co-Authored-By` и упоминаний ИИ-ассистентов в авторах** (требование владельца репозитория).
3. Пуш ветки: `git push -u origin <branch>`.
4. Если пользователь не просил иного — влить в `main`:
   ```bash
   git fetch origin main && git merge --no-commit --no-ff origin/main
   ```
   - **конфликтов нет** → завершить мерж, `git checkout main && git merge <branch> && git push`, вернуться на ветку;
   - **конфликты есть** → `git merge --abort`, ветку оставить как есть, в `main` не лезть и написать файл (см. ниже).

### Файл о конфликте

`improvements/merge-conflicts-ГГГГ-ММ-ДД.md`:

- какие файлы конфликтуют и на каких участках (`git diff --name-only --diff-filter=U`);
- что изменилось на «их» стороне — высокоуровнево, по коммитам `git log --oneline HEAD..origin/main`, а не по строкам;
- как это влияет на наш код: что сломается, какие решения расходятся (модель данных, контракт, справочники, поток занятия);
- предлагаемый способ разрешения и чьё решение считать основным.

Сказать пользователю одной фразой, что мерж не сделан и почему, со ссылкой на файл.

## 4. Экономия лимитов

- Искать `Grep`/`Glob` по конкретным символам, не читать файлы целиком; в больших файлах читать диапазон строк.
- Правки в нескольких местах — одним python-скриптом в scratchpad с `assert` на уникальность якоря, а не десятком мелких правок.
- Тяжёлое (`mvn clean verify` в Docker, `vinext build`, `docker compose build`) запускать один раз перед пушем, а не после каждой правки; на промежуточных шагах — `mvn -q -o compile` и `npm run lint`.
- Скриншоты и `.docx` разбирать по одному кадру, обрезая нужную область, а не пачкой.
- Не пересказывать пользователю дифф — он его видит; писать вывод и последствия.

## 5. Что нельзя без явной просьбы

- Пушить в `main` напрямую, делать `--force`, переписывать историю.
- Коммитить `materials/` (в `.gitignore`), выгрузки чата, дампы, `target/`, `node_modules/`.
- Менять версию контракта `X.Y` в `ContractVersionFilter` (ломает фронтенд) — правится только патч-версия в `openapi.yaml`.
- Трогать файлы пользователя в `improvements/` (`bugs_*`, выгрузки) — читать можно, править нет.
